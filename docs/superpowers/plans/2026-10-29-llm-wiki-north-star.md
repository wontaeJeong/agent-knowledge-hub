# LLM Wiki North Star 문서화 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Agent Knowledge Hub의 궁극적인 목표를 Agent-Native Knowledge & Experience Platform으로 명문화하고 새 에이전트 세션의 일관된 설계 판단과 검증을 지원한다.

**Architecture:** `docs/LLM_WIKI_CORE.md`를 제품 철학의 단일 기준으로 삼는다. 개발 지침은 `AGENTS.md`, 런타임 유지 규칙은 `wiki/SCHEMA.md`, 평가 설계는 `docs/EVALUATION.md`, 현재 격차와 단계는 `docs/ROADMAP.md`로 나눈다. 기존 구현 설명·요구사항을 보존하고 상호 링크로 연결한다.

**Tech Stack:** 한국어 Markdown 문서와 기존 저장소 검증 명령. 애플리케이션 기능·의존성·모델 계약 구현은 추가하지 않는다.

**Spec:** 사용자의 「Agent Knowledge Hub — LLM Wiki North Star 문서화」 요청 및 [Karpathy 원전](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f). 기존 기준은 `docs/LLM_WIKI_CORE.md`, ADR 002, `docs/requirements/requirements.json`, `docs/requirements/core-requirements.json`이다.

## Global Constraints

- 원전의 Raw Sources / Wiki / Schema, Ingest / Query / Lint, 지속적·누적적 연결 지식과 질문 결과 재편입을 보존한다.
- 원전에도 갱신·상충 표시·근거 인용이 있다. 이를 프로젝트만의 발명으로 분류하지 않고, 프로젝트의 운영 계약·측정 방법 확장과 구분한다.
- 제품 이름은 `agent-knowledge-hub`, 비전 표기는 Agent-Native Knowledge & Experience Platform이다.
- 목표·계획·현재 구현·실제 검증 결과를 구분한다. 새 평가 시나리오는 수행 결과가 아닌 계획이다.
- 기존 239개 + CORE 12개 요구사항, 35개 인수 시험 계획, 제품 기능과 보안 불변식을 삭제·축소·완료 승격하지 않는다.
- Vector DB·Graph DB·Markdown·API·MCP는 수단이다. 사람의 탐색·검토·승인을 유지한다.
- North Star의 의미 변경은 사용자/제품 책임자의 명시 승인과 근거·영향 검토가 필요하며 일반 구현 작업에서 임의 변경하지 않는다.
- 앞선 이름 변경 작업을 보존한다. 기존 브라우저 데이터 호환용 키와 외부 원전·다른 프로젝트 이름은 예외다.

## Review Focus

1. 문서/링크 수 증가만으로 지식 누적을 주장하지 않는지: 새 근거가 결론·조건·연결·재사용 품질을 개선하는 비교 시나리오로 검토한다.
2. 추론·파생 답변이 독립 증거로 순환 인용되는지: 계보 추적·확인 보류·반증 사례를 평가 설계에 포함한다.
3. 서로 다른 시점/환경의 주장을 모순으로 오판하거나 오래된 사실을 현행으로 사용하는지: 시간·맥락을 분리한 수용 시나리오로 검토한다.
4. 위키를 쓴 에이전트의 개선이 모델/도구/예산 차이나 평가셋 유출 때문인지: 대조군·동일 조건·홀드아웃·반복 실행·실패 포함 분모를 요구한다.
5. 새 세션이 비전 문서를 제품 완료 근거로 오해하는지: 문서만 제공한 독립 리뷰에서 사용자의 일곱 질문에 답하게 하고 현재 미구현 사항을 확인한다.

## Task 1: 제품 기준과 공통 에이전트 컨텍스트

**Files:** 수정 `docs/LLM_WIKI_CORE.md`, `AGENTS.md`, `CLAUDE.md`, `README.md`.

**Interfaces:** North Star가 설계 원칙을 소유하고, 나머지 문서는 링크로 참조한다. 기존 구현 설명과 경로를 유지한다.

- [ ] 원전과 현재 문서를 대조해 원래 제안 / 프로젝트 확장 / 현재 데모의 세 구분을 작성한다.
- [ ] North Star에 제품 목표, RAG·Memory·일반 Wiki와의 차이, 지식 발전 순환, Product Invariants, Non-Goals, 아키텍처 판단 질문을 작성한다. 기존 시스템도 이 패턴을 구현할 수 있음을 명시해 단순한 기술 이분법을 피한다.
- [ ] 장기 확장인 경험 추상화·재사용 교훈, 근거·신뢰·계보, 시간·맥락·상충 해소, 에이전트 소비/환류, 지속 평가와 후속 작업 개선을 정의한다. 승인만으로 진실이 보장되지 않음을 명시한다.
- [ ] North Star 변경은 명시 승인·변경 이유·트레이드오프·요구사항/평가 영향 기록을 요구한다. 충돌하는 설계는 우회하지 말고 예외 근거와 미충족 조건을 남긴다.
- [ ] `AGENTS.md`의 기존 안전·권한·발행·검증 규칙을 보존하면서 작업별 참조표와 설계 판단 규칙을 추가한다. `CLAUDE.md`는 공통 지침 참조만 남긴다.
- [ ] README에 비전과 평가 링크를 추가하되 로컬 데모 제한을 그대로 유지한다.
- [ ] 검토: 원전의 각 핵심 개념과 사용자의 일곱 질문이 어느 절에 대응하는지 확인한다.

## Task 2: 평가 계약·격차·런타임 규칙

**Files:** 생성 `docs/EVALUATION.md`; 수정 `docs/ROADMAP.md`, `wiki/SCHEMA.md`, `docs/AGENT_HANDOFF.md`; 필요 시 검증 결과를 `docs/TESTING.md`에 추가한다.

**Interfaces:** 평가 문서는 North Star를 검증할 방법을 정의하고 로드맵은 해당 평가와 기존 요구사항 ID를 연결한다. 런타임 규칙은 개발 지침이나 미구현 서버 통제를 대신하지 않는다.

- [ ] 평가 문서에 고정 데이터/근거·실행 추적·위키/모델/정책 버전, 측정 단위·분모·실패·미실행 처리, 사전 합의할 통과 기준과 결과 기록 양식을 작성한다. 근거 없는 목표 수치를 확정하지 않는다.
- [ ] Knowledge Compounding은 동일 질의/과제의 갱신 전후 비교와 원본만/정적 위키/유지 위키 대조군으로 설계한다. 중복 유입과 잘못된 답변 재편입이 품질 증가로 계산되지 않도록 한다.
- [ ] Knowledge Evolution 시나리오에 추가 근거, 반증, 시간에 따른 대체, 환경별 예외, 질문 결과 재편입, 실패 경험의 조건부 교훈, 원본 정정/권한 철회 전파와 이전 지식 회귀를 포함한다.
- [ ] Provenance·Contradiction·Temporal Knowledge에 정답 근거, 오탐/미탐, 해소 근거, 유효 시점과 기록 시점, 보류/거절 기준을 명시한다.
- [ ] 에이전트 성공률은 같은 모델·도구·과제·예산·권한 조건의 짝지은 반복 실험, 홀드아웃/누출 통제, 성공 수/전체 과제 수, 불확실성·비용·지연·안전 회귀와 함께 평가한다.
- [ ] 로드맵의 기존 전체 이행표는 유지하고 목표별 현재 근거·격차·후속 단계·평가 연결을 추가한다. 오프라인 검사와 실제 모델 의미 종합 평가를 분리한다.
- [ ] `wiki/SCHEMA.md`에 런타임의 근거 보존·추론 구분·시간/맥락·상충·경험·환류 규칙과 목표/현재 보장 경계를 명시한다. 정책 의미를 변경한다면 버전/미결 변경안 재검토 영향을 별도 승인 대상으로 보고하며 이번 문서 작업에서 코드 버전을 임의 변경하지 않는다.
- [ ] 인계에 관련 요구사항 ID, 변경 파일, 실제 검증, 남은 제약을 기록한다. 앞선 이름 변경에 따른 환경변수 변경과 기존 규칙 버전 변경안의 재생성 필요도 기록한다.

## Task 3: 검증·리뷰·전달

- [ ] Markdown 내부 상대 링크를 검사하고 모든 기존 요구사항/로드맵 데이터가 보존됐는지 diff로 확인한다.
- [ ] 독립 리뷰어에게 새 문서와 일곱 질문만 제공해 답변·모호함·원전 오인용·현재 구현 과장을 확인받는다. 문서의 문자열 존재만 검사하는 테스트는 추가하지 않는다.
- [ ] `npm test`, `npm run check:requirements`, `npm run build`, `git diff --check`를 실행해 실제 결과와 경고를 기록한다. 문서 작성이 의미 품질 평가 수행을 뜻하지 않음을 명시한다.
- [ ] 도구 생성물 `.serena/`, `.playwright-mcp/`는 커밋에서 제외하고 기존 변경을 삭제하지 않는다.
- [ ] 검증된 변경을 커밋·푸시하고 PR을 생성한다. 기본 디렉토리의 `main`과 작업 워크트리 연결을 확인하고 PR URL·검증 결과·미검증 범위를 보고한다. 명시 승인 전 병합하지 않는다.
