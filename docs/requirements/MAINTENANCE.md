# 요구사항 정비와 다음 구현 기준

2026-11-14. 251개 요구사항과 `main@9883fbe` 주요 경로를 대조한 작업 기준이다. [현재 구현 현황](../CURRENT_STATUS.md)을 함께 읽는다. **기존 필수 236개·확장 12개·선택 3개, 원래 수용 기준과 첫 운영 전 필수 조건을 유지한다.** 아래 개발 순서와 보완 검증은 면제·운영 승인·새로운 완료 선언이 아니다.

## 판단과 유지할 원칙

North Star의 연결 지식·근거·조건·경험 환류는 일관된 방향이다. 원본 권한의 상한, 승인 내용/기준 버전 고정, 의존 집합 일괄 발행, 현재 권한 재검사와 실패의 정직한 표시는 모든 경로에서 유지한다. 사람의 탐색·수정·검토 경험과 기존 제품 전체 요구사항도 보존한다.

현재 분류는 251개 중 236개가 필수라 개발 순서를 결정하기에 부족하다. 기능군별 작업에 다음 네 축을 병기한다. `priority` 필드의 기존 필수/확장/선택 의미를 재사용하거나 변경하지 않는다.

| 축 | 기록할 내용 | 예 |
| --- | --- | --- |
| 위험도 | 실패 시 누출·손실·잘못된 권고·업무 지연 중 어떤 영향이 있는가 | 원본 ACL 누출은 기능 편의성과 무관하게 차단 조건 |
| 적용 조건 | 경로/자료/주체/환경과 비활성 경로의 통제까지 명시 | 토큰 기능의 철회·범위 상한, 실제 도구 수집의 세션 결합 |
| 개발 순서 | 아래 W0~W3의 의존 관계와 완료할 업무 경로 | 결과 보고→재검토→기존 지식 갱신 |
| 증거 상태 | 구현·연결·자동 검증·운영 인수를 독립 기록 | 서비스 있음 / HTTP 차단 / 단위 시험 있음 / 사내 인수 없음 |

적용 조건은 필수 항목을 비활성화해 운영 조건에서 제외하는 수단이 아니다. 필수의 범위·수용 기준·출시 조건 변경은 GOV-010에 따라 사유·위험·대안·대체 통제·복구 계획·제품 책임자 승인을 별도로 남긴다. 이번 정비에서 그 변경은 하지 않는다.

## 다음 구현 순서

작업 식별자 W0~W3은 요구사항 ID가 아니며 새 인수 항목 수에 합산하지 않는다. 보안/손실 차단은 순서와 무관하게 선행하며 운영 개시는 기존 필수 게이트를 따른다.

| 순서 / 담당 역할 | 대상 요구사항 | 검토 가능한 결과와 종료 근거 |
| --- | --- | --- |
| W0 현황·결정 정리 / 제품·QA·운영 | GOV-007~010, IAM/ACL, NFR-001 | 실행 경로와 차단을 구분하고 첫 업무 사례·부하 등급·기존 공간 이관 결정을 기록한다. 이번 PR은 문서 정비이며 나머지 결정은 미확정이다. |
| W1 지식 갱신과 평가 / 지식 엔진·모델·도메인 검토자 | CORE-003~007·010~012, KNO-002~006·009·012~014, EVA-001~006 | 새 근거/반증으로 기존 결론·조건·연결을 수정하는 변경안을 검토·발행하고 기존 정답의 회귀와 후속 업무 결과를 측정한다. 결과 보고/정련 기반을 재사용한다. |
| W2 실제 업무 연결 / API·UI·작업 런타임 | QNA-005·008, CORE-009~011, CLB-003, VER-004~008, EDT-002 | 개인 대화의 trusted context·큐·모델 저장·화면 및 필요한 재검토/버전 경로를 연결한다. 현재 ACL·삭제 범위·멱등성·실패 복구를 실제 HTTP/DB에서 확인한 경로만 활성화한다. |
| W3 운영 차단 해소 / 보안·플랫폼·연동·QA | COL-003·005·008, IAM/ACL, LIF-005~007, VER-012, OPS, NFR, EVA-007~010 | 실제 도구 하나의 신뢰 가능한 수집, 기존 공간 이관, 삭제·복구·보존 연결과 사내 환경 인수. 기존 35개 인수 시나리오 및 항목별 기준을 모두 추적한다. |

W1의 안전한 실험에 필요한 W2/W3 작업은 먼저 수행한다. 번호는 모든 작업을 한 대형 PR로 묶거나 사내 운영을 먼저 시작하라는 의미가 아니다. 실제 변경은 [PR 운영 기준](../PR_WORKFLOW.md)의 작은 검토 단위로 나눈다.

## 원래 기준에 더해 확인할 행동

다음 사례는 원래 수용 기준을 삭제·대체하지 않는 **미실행 보완 검증 설계**다. CORE-003의 주제와 두 개념 페이지 사례도 계속 검증한다. 제품 목표·런타임 규칙 의미를 변경하지 않으며 구현에 들어갈 때 세부 데이터/판정자를 고정한다.

| 대상 | 보완 사례 | 관찰할 결과 |
| --- | --- | --- |
| CORE-003, KNO-001·005·006 | 기존 지식과 같은 조건의 반증, 다른 환경의 실패, 중복 자료를 각각 편입 | 반증은 기존 결론의 재검토, 다른 환경은 조건/예외 보존, 중복은 불필요한 새 페이지·버전 억제. 페이지 개수만으로 종합 품질을 판정하지 않음 |
| CORE-006, QNA-007, KNO-003 | 같은 원본을 인용하는 답변을 반복 재편입하고 새 조건을 포함한 답변도 제출 | 중복·기존 페이지 보완·별도 분석의 이유를 제시. 원본 계보와 기준 버전 유지, 독립 근거 수 증가 없음. 현재 새 답변 페이지 생성 경로의 확장 작업 |
| KNO-004, GOV-004 | 검토 완료지만 실행 미검증인 지식, 공식 채택됐지만 오래된 조건의 지식 | 검토·실행 검증·공식성·현재 적용 가능성을 독립적으로 표시하고 어떤 증거로 바뀌었는지 확인 |
| CORE-012, EVA-001~006 | 최소 세 차례 자료 추가·질문·점검을 실제 편입/검토/발행 경로로 실행 | 동일 원본·예산의 원본만/정적 위키/유지 위키 대조, 원본 지지·조건·반증 반영·기존 정답 회귀·총 유지 비용. 사전 작성 위키의 응답 비교와 구분 |
| EVA-002·003·005 | 인용은 존재하지만 주장을 지지하지 않는 답, 근거 없는 질문, 보호 구간 변경 | 문자열 검사와 독립 의미 판정 분리. 제안 기준인 대표 답변 100개·중요 주장 근거 일치율 95%, 변경 50개 안전 기준을 보존하고 주장별 분모·표본·판정자를 사전 고정 |
| GOV-009, UX-002~003, NFR-009 | 원본 공개 검토와 지식 검토를 거쳐 여러 관련 문서를 갱신 | 단계별 대기/실제 검토 시간, 원인별 묶음 수, 반려·재제안·재검토 수를 기록. 독립 검토를 생략해 속도 향상으로 보고하지 않음 |

단일 사례의 개선은 전체 지식 품질이나 에이전트 성능 개선을 뜻하지 않는다. 후속 업무 성공률은 독립 실행 기준과 홀드아웃을 사용하고, 미완료·실패·시간초과를 배정 분모에서 빼지 않는다. 평가 중 답변을 평가 위키로 재편입하지 않는다. 상세 설계는 [평가 계약](../EVALUATION.md)을 따른다.

## 수치와 제품 결정

- **부하:** 초기 10명 이하, NFR-001의 계정 1,000/동시 활성 100/발행 페이지 10만/버전 100만 가정, 전사 확대 계획을 서로 다른 시험 등급으로 기록한다. 현재 수치는 제안/가정이며 인수값을 확정할 제품·운영 담당자의 결정이 필요하다. NFR-002~008의 가용성·지연·복구 목표를 임의로 낮추지 않는다.
- **검토 비용:** UX-003·NFR-009에 이미 포함된 요구를 계측으로 구체화한다. 기간·건수·작업 복잡도·미완료 대기와 중앙값/p95를 함께 제시하며 목표값은 업무 표본 확인 후 평가 전에 정한다.
- **권한 호환:** 기존 3역할 보존 요구와 소유권 없는 공간 격리의 차이는 미충족이다. reviewer를 Owner로 추정하거나 차단을 해제해 봉합하지 않는다. [현재 현황](../CURRENT_STATUS.md)의 두 해결 경로에 대해 별도 결정한다.
- **일정과 검색:** Daily/Weekly 및 SRH-001의 검색 평가 요구를 보존한다. 작업 빈도·색인 기술 도입을 성과로 세지 않고 실제 변화 반영·관련 문서 탐색·예산·최소 변경을 확인한다.

## 상태 기록 양식

```text
요구사항 ID / 확인 커밋 / 담당 역할 / 확인일:
위험도와 근거 / 적용 조건 / 개발 순서 및 선행 작업:
구현: 없음 | 일부 | 기준 전체 구현 주장과 근거
연결: 독립 모듈 | 일부 연결 | 실제 경로 연결 | 비활성/차단
검증: 미실행 | 실행 실패 | 지정 환경에서 통과 (명령·커밋·결과 링크)
운영 인수: 미검증 | 미충족 | 승인된 환경/범위와 인수 기록
원래 수용 기준 / 보완 시나리오 / 남은 소프트웨어·정책·환경 조건:
```

기존 JSON의 `status`와 `demoCoverage`는 이 네 축을 대신하지 않는다. 초기 생성물의 `미구현`·`미검증`을 현재 기능 부재로 해석하지 않는다. [원래 35개 인수 시나리오](acceptance-tests.md)는 통합 시나리오이고 개별 회귀 테스트의 수가 아니다. 새 검증 증거는 현재 현황과 인계에 연결하며 원래 기준을 그대로 보존한다.
