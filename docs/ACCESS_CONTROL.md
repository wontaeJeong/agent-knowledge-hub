# 로컬·개인·팀 지식의 GitHub식 권한 모델

> **상태: 설계 제안 / 미구현 / 신규 수용 시나리오 미실행 (2026-10-30).** 기준 코드는 `main@ec148ef9`다. 이 문서는 후속 구현 계약이며 현재 서버에 역할·토큰·팀 관리 기능이 추가된 것은 아니다. 결정 이유는 [ADR 005](adr/005-github-style-access-control.md), 현재 실행 범위는 [운영 설정](OPERATIONAL_SETUP.md)을 따른다.

## 1. 제품 모델

**로컬은 저장·실행 위치, 개인·팀은 소유권이다. 지식 공간마다 공개 범위와 역할을 따로 부여한다.** GitHub의 사용자/Organization → Repository → Collaborator/Team 구조를, 사용자/팀 → 지식 공간 → 사용자/접근 그룹 구조로 적용한다.

예를 들어 `@alice/personal`은 Alice의 개인 공간, `@ax/platform`은 AX팀 소유의 지식 공간이다. Alice가 두 공간 모두에 참여해도 역할은 서로 다르다. `@ax/platform`의 Write가 `@ax/security`나 다른 사람의 개인 공간으로 전파되지 않는다. 경로는 표시용이며 권한과 참조는 변경되지 않는 ID를 사용한다.

| 축 | 값과 의미 | 다른 축에 미치는 영향 |
| --- | --- | --- |
| 저장 위치 | 로컬 전용 작업본 / 서버 개인본 / 허용된 공유본의 로컬 캐시 | PC에 있다는 이유로 소유권·공유·반출 권한이 생기지 않음 |
| 소유 네임스페이스 | 개인 사용자 또는 팀 | 팀 소유 지식은 작성자 퇴사 후에도 팀에 남음 |
| 지식 공간(Space) | 근거·페이지·변경 집합·발행 정책의 관리 단위 | GitHub Repository에 대응. 실제 Git 저장소일 필요 없음 |
| 공개 범위(Visibility) | Private / Team / Company | 기본 열람 대상만 정하며 편집·검토·공식성을 부여하지 않음 |
| 공간 역할(Role) | Read / Triage / Write / Maintain / Admin | 해당 공간에서 할 수 있는 작업 |
| 자료 제한·반출 정책 | 문서별 독자, 원본 계보, 로컬 복사·내보내기·모델 전송 허용 | 모든 역할보다 우선하는 상한 |
| 공식성 | 개인 해석 / 팀 결정 / 공식 기준 | 공개 범위·발행 여부와 독립. 공식 기준은 담당 부서 검토 필요 |

로컬 전용 자료는 사용자가 **서버 개인 공간으로 가져오기**를 선택하기 전 업로드하지 않는다. 반면 이미 연결한 서버 개인본은 기존 결정대로 호스트 연결 중 자동 동기화한다. 공유본 수정은 개인 파생본을 만들며 공유 발행본을 덮어쓰지 않는다. 연결 종료 후 동기화 daemon·OS 서비스·시작 프로그램·예약 작업은 제공하지 않는다. 서버의 지속 작업 요구사항은 유지한다.

## 2. 소유권과 멤버십

| 주체/관계 | 권한과 경계 |
| --- | --- |
| 개인 Owner | 본인 개인 공간 관리. 첫 구현의 개인 공간은 본인 전용이며 다른 사람 초대 대신 팀 공간으로 변경 제안 |
| 팀 Owner | 팀 멤버·그룹·팀 정책·소유권 관리, 팀 소유 모든 공간의 Admin. 타인의 개인 공간에는 접근하지 못함 |
| 팀 Member | 팀에 참여한 상태. 공간 기본 권한은 `none`이며 멤버 가입만으로 Private 공간 접근 불가 |
| 접근 그룹 | 같은 팀의 활성 멤버 집합. 공간별 역할을 일괄 부여. 첫 구현은 중첩 없는 그룹이며 그룹 관리는 팀 Owner 담당 |
| 공간 Collaborator | 팀의 활성 멤버/그룹에 부여한 공간 역할. 다른 팀원은 해당 팀에 먼저 가입해야 함 |
| 서비스 주체 | 팀 소유의 비인간 신원. 지정 공간·작업만 허용하며 사람 Owner나 검토자가 될 수 없음 |
| 시스템 운영자 | 배포·장애·계정 중지 등 운영 권한. 제품 역할만으로 모든 개인/팀 본문을 열람하거나 발행하지 못함 |

첫 구현은 개인 Owner 1명, 팀 Owner 1명 이상을 유지한다. 마지막 팀 Owner의 탈퇴·강등·삭제는 거부하고, 대상자가 수락한 소유권 이전과 이전 Owner 변경을 하나의 트랜잭션으로 처리한다. 개인 공간 양도·계정 병합은 별도 정책 없이 제공하지 않는다. 서비스 주체에는 필수 담당자와 만료 정책을 둔다.

팀 생성은 회사 정책이 허용한 활성 사내 사용자에게 `team.create`로 부여하고, 생성자가 첫 Owner가 된다. 생성 권한만으로 다른 팀을 관리할 수 없다. 초기 배포의 기존 공간 소유자는 검증된 subject를 사용하는 명시적 이관 설정으로 지정한다. 팀/그룹/공간 역할 초대는 수락 전 권한을 주지 않으며 만료·취소할 수 있다. 외부 디렉터리 그룹의 자동 가입은 회사가 승인한 명시적 관리 바인딩에만 적용한다.

팀 탈퇴/제명은 그 팀의 직접 역할·그룹 경로·팀 위임 토큰을 함께 무효화한다. **그룹 하나에서 제외한 것**은 그 경로만 없애므로 다른 직접 역할이나 공개 범위로 얻은 권한은 남을 수 있다. 팀에서 나가도 Company 독자 자격을 별도로 유지하면 Company 공개본은 계속 읽을 수 있다. 퇴사/계정 중지는 모든 활성 세션·위임을 차단한다. 이미 작성한 팀 지식의 작성자·계보·감사 이력은 보존한다.

시스템 운영자의 DB 접근은 별도 인프라 신뢰 경계다. 이 제품 권한 모델이 DB 운영자의 기술적 접근까지 차단한다고 주장하지 않는다.

## 3. 공간 공개 범위

| 공개 범위 | 기본 독자 | 생성/변경 조건 |
| --- | --- | --- |
| Private | 개인: 본인만. 팀: 명시적으로 권한을 받은 멤버/그룹과 팀 Owner | 모든 새 공간의 기본값. 팀 멤버 전체를 자동 추가하지 않음 |
| Team | 소유 팀의 활성 인간 멤버에게 발행본 Read | 팀 공간만 가능. 공간 Admin의 명시적 변경 및 영향 검토 |
| Company | 같은 배포 환경의 허용된 사내 디렉터리 구성원에게 발행본 Read | 팀 공간만 가능. 회사 정책이 허용한 공간 Admin 및 담당 부서 공개 검토 |

Company는 인터넷 공개나 익명 접근이 아니다. SSO 로그인 성공만으로 사내 독자 자격을 인정하지 않으며 외부 계정·서비스 주체를 자동 포함하지 않는다. Team/Company의 기본 Read는 발행본만 대상으로 하고 미발행 변경안·개인 초안·원본 목록 전체를 공개하지 않는다. 특정 원본/문서의 더 좁은 제한은 계속 적용한다.

첫 구현은 익명 Public·외부 Guest·소지자에게 권한을 주는 링크 공유를 활성화하지 않는다. Company 기본 독자 확대도 SHR-010의 선택 정책이며 기본 비활성이다. 링크 복사는 이미 권한 있는 사용자의 탐색 수단이다. SHR-010~012의 선택 요구사항은 삭제하지 않으며, 활성화 전 별도 정책·구현·회귀가 필요하다.

SHR-004~009의 **인증된 수신자 지정 공유는 필수 기능으로 유지한다.** 명시적인 사용자/그룹, 대상 공간·문서/버전·자식 포함 범위, 허용 작업, 만료를 고정한 범위 제한 grant로 처리한다. 팀의 활성 멤버만 새 독자로 지정할 수 있고 나머지 공간 열람·편집 권한은 생기지 않는다. 역할·원본·상위 제한·반출 상한을 넘지 못하며 미래 자식에 자동 확대하지 않는다. Admin이 관리하고 자신이 읽거나 공유할 수 없는 원본을 공개할 수는 없다. 현재 접근으로 링크만 만드는 것과 이 새 grant를 부여하는 동작을 UI/감사에서 구분한다. 철회/만료는 다음 본문·첨부·변환본 요청에도 적용한다.

Private → Team → Company 변경, 공간 이동, 신규 멤버·그룹 추가는 접근 확대다. 서버는 새 독자와 영향받는 원본/파생본/버전을 계산해 미리 보여준다. 근거가 허용하지 않으면 명시적인 더 좁은 자료 제한을 유지하거나 변경을 거부한다. 메타데이터만 넓히고 제한 본문을 함께 노출하지 않는다. 공개 범위를 줄이면 검색·링크·캐시·기존 답변에도 새 제한을 적용한다.

## 4. GitHub식 공간 역할

역할은 다음 순서로 작업 집합을 포함한다. **Read < Triage < Write < Maintain < Admin.** Triage는 검토 큐 운영, Maintain은 지식 검토·발행 책임, Admin은 공간 접근·설정 관리에 대응한다. 이 매핑은 제품 설계이며 GitHub 권한표의 그대로 복제는 아니다.

| 작업 | Read | Triage | Write | Maintain | Admin |
| --- | --- | --- | --- | --- | --- |
| 허용된 발행본·고정 버전 검색/열람·질문 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 읽을 수 있는 문서에 댓글·자기 댓글 수정 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 개인 파생본 만들기 | 조건부 | 조건부 | 조건부 | 조건부 | 조건부 |
| 팀 변경안 큐 분류·중복 표시·검토자 요청 | — | ✓ | ✓ | ✓ | ✓ |
| 원본 등록·공유 변경안 작성/수정·제출·Lint 실행 | — | — | ✓ | ✓ | ✓ |
| 변경안 승인/반려·승인 집합 발행 | — | — | — | 조건부 | 조건부 |
| 문서 보호·검토 정책 강화·발행 중지·보관 | — | — | — | ✓ | ✓ |
| 공간 역할 부여/회수·공개 범위·설정 관리 | — | — | — | — | ✓ |
| 공간 이전·삭제, 보호 정책 완화 | — | — | — | — | 조건부 |

- 개인 파생본에는 읽기와 별도의 `local.copy`/개인 저장 정책이 필요하다. Read는 내보내기·로컬 복사·모델 전송 허가를 포함하지 않는다.
- Triage 이상의 큐 접근에도 변경 집합 **전체 입력 계보**를 읽을 권한이 필요하다. 요청할 검토자는 이미 자격을 가진 사람 중에서 고른다. Triage가 자신을 검토자로 임명할 수 없다.
- Write는 **공유 초안과 변경 제안**을 쓸 수 있다는 뜻이다. 공유 정본·발행본·과거 버전은 직접 덮어쓰지 못한다. 다른 사람의 개인 초안은 볼 수 없다.
- Maintain/Admin도 §6의 보호 규칙과 문서 유형별 검토자 지정을 통과해야 승인·발행할 수 있다. 높은 역할, 팀 Owner, 서비스 주체의 담당자라는 이유로 승인 생략 권한은 생기지 않는다.
- 지정 검토자 목록 변경은 Admin/Owner가 관리한다. Maintain의 정책 강화는 최소 승인 수·보호 범위를 늘리는 권한이며 자신을 새 검토자로 임명하는 권한이 아니다.
- 공간 삭제·다른 소유 네임스페이스로 이전은 소유 개인/팀 Owner만 최종 확정한다. 정책 완화는 Owner와 조직 최소 정책의 허용이 필요하며 이미 제출된 변경안에 소급 적용해 검토를 우회하지 않는다. 회사 공개나 공식 기준은 별도 담당 부서 권한도 필요하다.

개인 Owner는 자신의 공간에서 개인본을 저장·수정한다. 개인 저장에는 팀 검토를 강제하지 않지만, 타인 원본에서 파생된 개인본의 제한·계보는 유지한다. 팀 공유나 공식 기준으로 바뀔 때 목적지 정책을 새로 적용한다.

## 5. 실효 권한 계산

서버의 공통 `authorize(subject, action, resource, context)` 계약을 REST·웹·MCP·동기화·작업자·다운로드에 적용한다. 아래 이름은 **제안 계약**이며 현행 함수/DTO가 아니다.

1. 신원과 배포 환경을 검증한다. 사용자 비활성, 세션/토큰 만료·철회, 팀 자격 상실이면 거부한다. 클라이언트가 보낸 사용자/팀/역할 이름을 신원으로 사용하지 않는다.
2. 대상 공간·자원·작업에 유효한 grant만 고른다. 개인/팀 Owner의 소유 범위 Admin, 활성 멤버의 직접 역할·그룹 역할, 공개 범위 기본 Read 중 가장 높은 역할을 선택한다. 수신자 공유의 문서 한정 grant를 공간 전체 역할로 합산하지 않는다. 팀 기본 역할은 `none`이다.
3. 해당 역할이 작업을 허용하는지 확인한다. 위임 토큰은 허용 공간·작업·기한과의 **교집합**만 사용할 수 있다. 공개 범위 기본 Read는 원본/초안 관리 권한이 아니다.
4. 공간 경계, 문서의 모든 상위 제한, 원본/모델 전체 입력 계보의 현재 독자, 외부 원본 ACL 신선도, 삭제·철회·문서 보호를 검사한다. Admin/Owner에도 동일하게 적용한다.
5. 작업별 반출·모델 목적지·검토·예산 정책을 적용하고 응답 직전/발행 트랜잭션에서 다시 확인한다. 정책 저장소나 IdP 확인 실패 시 보호된 응답·변경을 차단한다.

`공간 역할 허용 ∩ 현재 자료/근거 접근 ∩ 위임 한도 ∩ 작업 정책`이 최종 허용 범위다. 여러 역할은 작업 권한을 합치지만 원본/상위 문서의 제한은 늘 좁히는 상한이다. 첫 구현은 별도 사용자별 deny 우선순위 언어를 만들지 않는다. 계정/토큰 중지·팀 자격 및 자료 제한으로 명시적으로 차단한다.

문서/폴더의 **제한 설정**은 grant를 좁힐 수만 있고 새 권한을 부여하지 않는다. 신규 수신자에게 권한을 줄 때는 §3의 별도 범위 제한 grant와 현재 공간/원본 공유 검사를 통과해야 한다. 부모가 넓어져도 제한된 자식은 그대로다. 문서를 이동할 때 기존 제한과 새 부모 제한의 교집합을 적용하고 새 독자/차단 대상을 미리 확인한다. 제한을 제거하려는 관리자도 근거 및 공개 확대 검사를 우회할 수 없다.

페이지·요약·질문 답변·Lint 결과·이전 버전·댓글/첨부·알림·제목·태그·검색 개수·추천·관계 그래프·내보내기를 같은 규칙으로 제공한다. 모델에 실제 전송한 전체 입력 계보를 보존하며 인용만 지워 제한을 없애지 않는다. 응답 직전에 철회되면 모델 작업 결과도 반환하지 않는다. 현재 구현의 전체 입력 계보 검사를 더 약한 인용 전용 검사로 교체하지 않는다.

다중 원본 파생본의 독자는 모든 근거/입력 독자의 교집합 이하다. **지정한 발행 독자가 그 교집합보다 넓으면 발행을 거부한다.** 더 좁은 문서 제한을 선택한 경우만 제한된 발행이 가능하며 조용히 독자를 바꾸지 않는다. 제한 원본을 팀원이 모두 읽을 수 없는데도 공간이 Team이라는 이유로 합성 본문을 공개하지 않는다.

ACL-006의 정제본 공개는 일반 발행과 별도다. 원본 공개 결정 권한을 가진 담당자가 정제본·공개 대상·근거·유효 범위를 검토해 별도 공개 결정과 새 공개용 자료를 기록해야 한다. 원본 자체와 기존 계보의 접근은 유지한다. 이 절차가 구현되기 전 해당 확대를 거부한다. 링크 숨김·본문 복사·LLM 민감정보 제거·Admin 승인만으로 독자 범위를 넓히지 않는다.

무권한 객체 ID 조회는 존재 여부를 구별하지 않는 `NOT_FOUND`, 이미 볼 수 있는 객체의 작업 권한 부족은 `FORBIDDEN`, 인증 만료는 `UNAUTHENTICATED`로 응답한다. 내용/담당자 이름을 노출하지 않는 일반 접근 요청을 허용하고, 중복/오입력/무권한 요청의 응답 형태를 통일한다. 관리자는 자신이 관리하는 범위 안에서만 허용 경로·차단 사유를 확인한다.

## 6. 개인 → 팀 공유와 보호 규칙

GitHub의 fork/PR/보호 브랜치 개념을 **개인 파생본 → 변경 집합 → 검토 → 발행본**으로 적용한다. 서버의 공유 발행본이 정본이며 로컬 동기화와 지식 Ingest → Query → Lint를 구별한다.

1. 팀 발행본을 허용 범위에서 개인 파생본으로 만든다. `(originSpaceId, pageId, baseVersion)`과 입력 계보를 보존한다.
2. 개인 revision을 수정·동기화한다. 공유본은 그대로이며 다른 개인 파일·대화·초안을 함께 제출하지 않는다.
3. 작성자가 목적지 공간, 선택한 개인 revision, 기준 버전, 관련 페이지/근거와 새 독자를 미리 확인한 뒤 **변경 제안**한다. 목적지 Write 이상과 원본/개인본 읽기·공유 정책이 모두 필요하다. Read/Triage 사용자는 개인본을 준비할 수 있지만 공유 제안 제출은 Write를 요청해야 한다.
4. 서버는 선택한 본문·revision·출처·전체 입력 계보·의존 변경을 스냅샷으로 고정한다. 목적지 검토자는 이 스냅샷만 읽고 작성자의 나머지 개인 공간에는 접근하지 않는다. 검토자가 읽을 수 없는 제한 입력이 있으면 제출/검토를 차단한다.
5. 자격 있는 사람이 고정 스냅샷을 검토한다. 발행 직전 작성자·검토자·발행자의 현재 권한과 독자/원본/정책/기준을 다시 확인하고 의존 변경 집합을 하나의 트랜잭션으로 발행한다.

공유 제출은 목적지에 검토 가능한 스냅샷을 전달하는 명시적 행위다. 개인 공간 Owner라고 해서 외부 원본 공개를 승인할 수는 없다. 선택 revision 이후의 개인 편집은 제출본을 바꾸지 않으며, 제안 회수도 이미 적법하게 남긴 검토·감사 보존 기록의 자동 삭제를 뜻하지 않는다.

본인이 공개 결정 권한을 가진 **자체 작성 자료**는 제출 화면에서 선택한 본문/원본과 대상 독자를 명시해 공개 결정을 기록하고, 검토용·발행용 새 자료 스냅샷으로 등록할 수 있다. 이는 개인 공간 전체 권한을 부여하지 않는다. 타인/외부 원본이나 제한 지식이 섞이면 그 계보와 각 원본의 별도 공개 결정을 모두 확인해야 한다. 단순 개인 저장·동기화·복사만으로 이 결정이 생성되지 않는다.

| 보호 항목 | 기본 정책 |
| --- | --- |
| 사람 검토 | 팀 발행은 독립 인간 검토자 1명 이상. 본인 제안의 자기 승인 금지, 에이전트/서비스 주체 승인 금지 |
| 검토자 자격 | 목적지 Maintain 이상 **그리고** 공간/문서 유형별 지정 검토자. 공식 기준은 담당 부서 검토 포함 |
| 고정 대상 | 본문·선택 개인 revision·근거/전체 입력 계보·기준 버전·독자 제한·정책 버전의 해시 |
| 승인 무효화 | 고정 대상 변경, 관련 ACL/멤버십/역할 버전 변경, 검토자 자격 회수 시 재검토 |
| 발행 | Maintain 이상인 인간이 실행. 검토자와 발행자는 같아도 되지만 제안자와 독립된 유효 검토 1명 필요 |
| 버전/재시도 | 기준 충돌이면 전체 차단. 동일 멱등 요청은 같은 결과. 복원은 현재 권한을 유지하는 새 변경 제안 |
| 관리 우회 | Admin/팀 Owner도 보호 정책 우회 불가. 초기 구현에 긴급 직접 발행 경로를 두지 않음 |

팀 Owner가 한 명뿐이어도 공유 자기 승인을 허용하지 않는다. 독립 검토자가 준비될 때까지 개인본/미발행 제안을 보존한다. 보호 정책 설정을 바꿔 승인자 자격을 즉시 우회하지 못하도록 최소 정책을 서버에서 강제한다. 파생 근거가 철회되면 개인 fork·제안·기존 답변도 그 제한을 유지한다.

인간 승인은 위임 도구와 분리된 사람 세션의 검토 경로로 기록한다. 요청의 `human=true`나 CLI 확인 플래그를 자격 증거로 사용하지 않는다. 승인 기록은 주체·대상·정책 검사를 증명할 뿐 실제 검토의 성실성이나 지식의 진실을 보장하지 않는다.

## 7. API·MCP·로컬 반출

현재 운영 MCP는 OIDC 쿠키 세션 경로다. 아래 Bearer/서비스 주체·범위 토큰은 **새 설계**이며 구현됐다고 표시하지 않는다. 현재 `wiki_*` 합성 커넥터와 `knowledge_*` 서버 도구는 자동 호환되지 않는다.

| 호출 주체 | 허용 범위 | 금지/별도 조건 |
| --- | --- | --- |
| 사람 웹 세션 | 현재 공간 역할과 자료 접근 범위 | 승인·관리·공유 확대는 사람 확인과 세션/CSRF·필요 시 재인증 |
| 사용자 위임 토큰 | 사용자 현재 권한 ∩ 발급 시 선택 공간/작업 ∩ 조직 정책 | 처음에는 읽기/등록/개인 동기화/변경 제안만. 승인·발행·멤버/공개/보호 정책 변경 불가 |
| 팀 서비스 주체 | 명시적 공간 역할 ∩ 토큰 작업 ∩ 서비스 정책 | 사람의 모든 권한 복제 금지. 팀 멤버십으로 Company/Team 기본 독자 자격 자동 부여 금지 |
| 로컬 커넥터 | 인증 사용자 개인본 및 허용된 공유본의 조회·연결 중 동기화·변경 제안 | 원본/첨부/전체 이력 일괄 복제 금지. 보호된 캐시의 완전 오프라인 열람 보장 없음 |

제안 작업명은 `knowledge.read`, `source.create`, `changeset.propose`, `personal.sync`, `local.copy`다. 실제 프로토콜 버전 결정 전 현행 토큰/도구에 이 이름을 추가했다고 가정하지 않는다. 외부 모델 전송과 일반 내보내기는 별도 정책이며 `knowledge.read`로 허용되지 않는다. `local.copy`도 현재 공간/자료의 `localCopyAllowed` 및 저장 정책을 넓힐 수 없다.

발급 시 대상 배포 환경·주체·위임한 사람/팀·담당자·정확한 공간 ID·작업·만료를 고정한다. 토큰의 권한 상한은 발급 후 편집하지 않으며 확대하려면 새 토큰을 발급한다. 사용자 현재 권한이 줄면 즉시 교집합이 줄고, 나중에 역할이 커져도 기존 토큰의 발급 상한은 커지지 않는다. 원문은 한 번만 보여주고 서버에는 검증용 해시·식별자·폐기/최근 사용 메타데이터를 저장한다. 자격증명은 로컬 상태/로그/모델 프롬프트에 저장하지 않는다.

발급 시에도 발급자가 현재 허용받은 공간·작업보다 넓은 상한은 거부한다. Read 사용자가 미리 제안 권한을 담은 토큰을 만들어 두었다가 나중에 역할 상승으로 활성화하는 경로를 허용하지 않는다.

팀 서비스 자격증명은 팀 Owner/권한 있는 공간 Admin이 명시적 공간 범위 안에서 관리한다. 개인 퇴사에 종속된 장기 공용 사용자 키로 대체하지 않는다. 담당자 변경·토큰 회전·팀 해산·계정 중지는 감사 대상이다. 이름/slug가 같아도 다른 공간/환경의 토큰은 사용할 수 없다.

캐시는 매 보호 조회 전 현재 권한·반출 정책을 확인한다. 철회가 확인되면 관련 캐시·충돌·병합안을 제거하고 원본에 종속된 개인 초안/미전송 제안은 열람·동기화·제출하지 않는다. 복구는 다시 허용된 뒤에만 가능하며 처리/보관 기준을 명시한다. 서버 확인 실패 시 내용을 제공하지 않되, 이미 복사한 평문·OS 백업의 완전 회수나 오류 중 디스크 삭제를 약속하지 않는다. 스스로 작성한 비종속 개인 자료는 팀 탈퇴로 삭제하지 않는다.

## 8. 서버 데이터와 인증 경계

새 개념 스키마의 최소 책임은 다음과 같다. 실제 DDL/마이그레이션은 별도 구현 PR에서 정의한다.

| 개체 | 저장할 핵심 정보 / 제약 |
| --- | --- |
| Principal | 내부 ID, 인간/서비스 구분, 인간은 검증된 issuer+subject, 활성 상태. 이메일/표시 이름을 PK로 쓰지 않음 |
| Namespace / TeamMembership | user/team 소유 ID, 팀 Owner/Member·상태·버전, 마지막 Owner 보장 |
| Space | 기존 `workspaces.id` 유지 + owner namespace·slug·visibility·정책 버전·상태. namespace 내 slug 유일 |
| Group / GroupMembership | 동일 팀 내 멤버만, 중첩 없음, 멤버십 버전 |
| SpaceGrant | space·principal/group·역할·자원/작업 한도·부여자·선택 만료·버전. 문서 한정 공유를 공간 전체 grant로 확장하지 않음 |
| ResourcePolicy / Provenance | 기존 `(workspace_id, kind, id)` 유지, 문서 상위 제한·원본 현재 ACL·신선도·반출 정책·전체 입력 계보 |
| PersonalDraft / ProposalSnapshot | 개인 owner, `(originSpaceId, pageId, baseVersion)`, 선택 revision, 별도 고정 제출본. 개인 공간 읽기 권한을 목적지에 주지 않음 |
| ReviewPolicy / Approval | 지정 검토자·최소 승인 수·공식성 정책, 제안 해시·정책/관련 ACL/역할 버전과 승인자 ID |
| Credential / AccessAudit | 토큰 해시·발급 상한·담당자·만료·철회, actor·위임 주체·대상·전후 권한·이유·추적 ID |

논리적 Space는 현행 DB의 `workspaces`에 대응한다. 현행 `Context.workspaceId`를 조직/테넌트 ID로 임의 재해석하거나 기존 resource ID를 전역 ID로 바꾸지 않는다. 새 API의 `spaceId`는 해당 경계에 매핑하고, 모든 참조는 공간+종류+ID+버전으로 확인한다. STG와 PROD는 기존 별도 DB/자격증명/엔드포인트를 유지한다.

OIDC는 신원을 증명하고 허용된 디렉터리/그룹 사실을 제공한다. 제품의 팀 소유권·공간 역할·검토 정책은 서버 정책으로 결정한다. 현행 `OIDC_GROUP_ROLES`가 로그인/매 요청에 단일 workspace 역할을 갱신하는 코드를 새 멤버십과 병행하면 수동 회수한 권한이 재생성될 수 있으므로 **전환 전 교체가 필요하다.** 외부 그룹 매핑도 명시적인 팀/공간 바인딩만 갱신하며 수동 grant·회수를 덮어쓰지 않는 관리 주체/우선순위를 정의한다. 철회된 관리 바인딩은 외부 상태에서 제거되거나 명시적으로 재승인되기 전 되살아나지 않는다.

초기에는 기존 PostgreSQL 안에서 역할/ACL/검토를 계산하고 현재 workspace 트랜잭션 경계를 확장한다. 외부 정책 엔진·그래프 DB는 필수로 도입하지 않는다. 멤버십/역할/ACL 변경과 발행은 같은 관련 정책 버전과 DB 잠금으로 직렬화하고, 발행은 승인 스냅샷·현재 자격·현재 독자 검사를 원자적으로 수행한다. 모델 호출 중에는 DB 잠금을 유지하지 않으며, 결과 반환/발행 시 최신 상태를 재검증한다.

권한 버전은 캐시 무효화 신호이지 권한 확인의 대체가 아니다. 서버 replica가 늘어도 프로세스 로컬 캐시만으로 철회 여부를 판단하지 않는다. 기동 스키마 호환성 차단을 유지하고 구/신 권한 경로 혼용을 허용하지 않는다. 감사에는 원문 본문·키를 남기지 않으며 외부 감사 보호/보관은 기존 SEC-010 운영 과제로 유지한다.

사용량은 본인 조회를 기본으로 하고, 팀/공간 집계는 별도 `usage.read_aggregate` capability를 가진 소유 Owner/공간 Admin의 해당 범위로 제한한다. Maintain/검토자 지정만으로 전사·다른 공간·다른 개인 사용량을 읽지 못한다. 기존 reviewer의 workspace 집계 권한을 새 역할에 암묵적으로 복제하지 않는다. 직원 개인 생산성 순위는 기본 제공하지 않는다.

## 9. 관리·공유 UX

다음은 **화면 사양**이며 새 라우트가 이미 구현됐다는 뜻은 아니다. 기존 UI의 디자인 토큰/프리미티브를 사용한다.

| 화면 | 필요한 행동 |
| --- | --- |
| 공간 선택 | `개인 / 팀 / 전사에서 찾기`와 공간 이름, 소유자, 공개 범위. 로컬 상태는 별도 `연결 중 / 미전송 n건 / 충돌 / 오류` 표시 |
| 공간 헤더 | `@ax/platform · Team · 내 권한 Write`, 문서가 더 제한되면 `일부 독자 제한` 표시. Company와 공식 기준 배지를 구분 |
| 접근 관리 | 사용자/그룹·역할·직접/그룹/공개 범위의 부여 경로·만료·담당자. 사용자별 실효 권한과 제한 사유 조회 |

| 역할 변경/제명 | 변경 전후 실효 역할, 다른 grant로 남는 접근, 무효화할 승인/토큰/캐시를 표시. 마지막 Owner 변경 거부 |
| 개인본 공유 | 목적지·선택 revision·diff·기준 버전·입력 근거·새 독자·제외된 개인 자료를 확인한 뒤 `변경 제안` |
| 검토/발행 | 검토자 자격·자기 승인 금지·유효 승인 수·원본/독자 충돌·재검토 사유 표시. 승인과 발행 상태 구분 |
| 반출/토큰 | 읽기와 로컬 저장 허용을 별도 표시. 토큰의 공간·작업·기한·최근 사용·폐기, 원문 재조회 불가 |
| 수신자 공유 | 기존 권한 링크 복사와 새 grant 부여 구분. 수신자·역할·문서/버전·자식 범위·만료·활성 공유/회수 경로 표시 |
| 권한 없음 | 본문·제목·멤버 목록을 먼저 렌더링하지 않고 일반 접근 요청 제공. API 최종 판단과 메뉴 노출을 일치시킴 |

설정 패널은 `접근 관리 / 검토·보호 / 공개 범위 / 연동 자격증명 / 위험 작업`으로 구분한다. Maintain에는 검토·보호 강화를, Admin에는 공간 관리, Owner에는 소유권/삭제를 권한에 따라 제공한다. 서버 응답의 실효 capability로 버튼/메뉴를 제어하고 프런트의 역할 문자열 비교를 보안 경계로 삼지 않는다. 역할을 잃으면 열린 diff·답변·검색·첨부 상태도 제거한다.

## 10. 현재 구현에서의 전환

| 현재 코드/규칙 | 새 계약과 전환 조건 |
| --- | --- |
| `reader/editor/reviewer` 단일 workspace 역할 | `reader → Read`, `editor → Write`, `reviewer → Maintain` 후보. Admin/팀 Owner를 reviewer 전체에 자동 부여하지 않음 |
| reviewer의 승인/발행 및 workspace 사용량 조회 | 기존 동작을 새 역할의 증거로 간주하지 않음. 지정 검토자·독립 승인·사용량 별도 capability를 명시적으로 이관 |
| `workspaces`, `resource_readers` | 기존 공간 ID·원본/문서 allowlist 보존. 소유 namespace를 검토해 매핑하며 미지정 자료는 격리. 누락 독자를 팀/전사로 채우지 않음 |
| OIDC 그룹→전역 3역할 갱신 | 신원과 팀/공간 바인딩 분리, 회수/정지의 우선순위 강제. 관리 권한 bootstrap은 검증된 내부 subject로 명시 지정 |
| 기존 승인·세션·설정 토큰 | 새 정책의 해시/독립 검토 조건이 없는 승인은 무효화. 구역할 세션/토큰은 재인증/재발급하며 자동 Admin/전체 공간 토큰으로 변환하지 않음 |
| 개인 커넥터의 `personal` 및 공간+ID 충돌 보호 | 개인 owner·기존 원격 공간 ID와 명시적 매핑. 전체 tuple을 보존하고 새 저장 형식/토큰 회전의 호환 마이그레이션 필요 |
| `scope: private/team/company` 문자열 | 표시 힌트와 서버 독자 정책을 구별. 문자열만으로 접근 허용하지 않고 실제 owner·grant·자료 제한에서 결정 |
| 전체 모델 입력 계보·DB 승인 ACL 해시 | 계속 유지·확장. 새 토큰/역할 적용 때문에 원본 권한·정책/기준 검사·원자 발행이 약해지면 전환 불가 |

기존 reviewer가 Admin/팀 Owner로 자동 승격되거나 독립 검토 없는 과거 승인이 발행되는 호환 경로를 만들지 않는다. 기존 개인 자료/개인 fork는 개인으로, 공유 자료는 명시적으로 지정한 팀 공간으로 이관하고 결과를 사전 출력한다. 소유권을 추정할 수 없으면 관리자 검토 대기 상태로 두며 자동 Team/Company 공개를 하지 않는다. 데이터/정책 백업·복구 시험과 마이그레이션 중 쓰기 차단이 필요하다. 구버전으로 롤백해 새 제한을 우회할 수 없도록 스키마/정책 호환성을 검사한다.

구현 순서는 다음과 같다. 모두 기존 운영 게이트 안의 작업이며 첫 실사용에 필요한 요구사항을 뒤로 제외하지 않는다.

1. **공통 모델:** namespace·팀/그룹·SpaceGrant·자료 제한·실효 capability·감사·OIDC 매핑을 서버 서비스와 마이그레이션으로 구현한다. 기존 원본 계보/발행 회귀를 보존한다.
2. **검토와 관리:** 지정 검토자·독립 승인·현재 권한 원자 재검사, 접근/공개/소유권/접근 요청 UI, 사용량 권한 이관을 연결한다.
3. **클라이언트 통합:** 개인 커넥터를 같은 서버 권한·공간 ID·변경 집합 서비스에 연결하고 제한 토큰/서비스 주체를 구현한다. 연결 중 동기화 수명주기를 유지한다.
4. **운영 검증:** 아래 AC 시나리오와 기존 인수 시험을 REST/MCP/웹/작업자/캐시에 적용하고 실제 IdP·DB·외부 ACL·반출/복구를 검증한다. 전체 기능/운영 인수와 지식 품질 평가는 별도 판정한다.

## 11. 권한 수용 시나리오

**AC-01~24는 설계 검증용 ID이며 전부 미실행이다.** 기존 `ACL-*` 요구사항과 혼동하지 않는다. 기존 251개 요구사항·35개 인수 시나리오의 수/상태를 변경하거나 이 표만으로 대체하지 않는다. 후속 구현에서 정상·거부·경쟁 조건의 실제 증거를 기록한다.

| AC-21 | reviewer/미소유 자료·과거 승인·구세션 마이그레이션 | 자동 Admin/공개 승격 없음, 미소유 자료 격리·승인 무효화·재인증 | ACL-001/006, REV-004, OPS-004 |
| AC-22 | 수동 회수 후 OIDC 재로그인/외부 그룹 동기화 | 폐기된 관리 바인딩을 자동 복구하지 않음, 관리 주체·이력 추적 | ACL-007/013, SEC-009 |
| AC-23 | 무권한 접근 요청/집계 조회, 권한 회수된 열린 UI | 제목/담당자·다른 공간 사용량 비노출, 보호 상태 제거, 결정 감사 보존 | ACL-010/011, GOV-009, UX-004 |
| AC-24 | Company 발행 또는 일반 팀 승인으로 공식 기준 표시 | 공개와 공식성 분리. 담당 부서 검토 없이 공식 기준 변경 거부 | GOV-004, REV-009 |

이 설계는 Ingest/Query/Lint가 안전하게 같은 지식을 재사용·갱신하도록 권한 경계를 정의한다. 문서 수나 동기화 성공을 지식 효과로 간주하지 않으며, 의미 품질·업무 성능은 [평가 계약](EVALUATION.md)의 대조 평가로 검증한다. 권한 회귀는 실패 0건을 목표로 기존 EVA-004와 함께 검증하되, 실행 전 결과를 주장하지 않는다.

## 12. 참고와 제품 선택

2026-10-30에 아래 GitHub 공식 문서를 확인했다. 역할/소유권/위임 원리를 참고하며, 사내 근거 교집합·사람 검토·반출 제한은 이 제품 요구사항으로 추가한다.

- [GitHub Repository roles](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization): Read/Triage/Write/Maintain/Admin과 저장소별 역할.
- [GitHub Organization roles](https://docs.github.com/en/organizations/managing-peoples-access-to-your-organization-with-roles/roles-in-an-organization): 조직 Owner/Member와 저장소·팀 관리의 범위 구분.
- [GitHub base permissions](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/setting-base-permissions-for-an-organization): 기본 권한과 추가 역할 경로. 이 제품은 기본 `none`으로 시작한다.
- [GitHub personal access tokens](https://docs.github.com/en/enterprise-cloud%40latest/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens): 토큰은 소유자의 권한을 넘지 않으며 범위로 더 제한한다.

전사 단일 역할은 공간 격리를 못 하고, 문서별 ACL만 두면 팀 권한 관리와 설명이 어려워진다. 공간 역할+좁히는 자료 제한은 관리 지점을 두 층으로 늘리는 대신 원본 파생 제한을 보존한다. 기본 독립 검토로 1인 팀의 즉시 공유 발행은 제한되지만 개인 작업은 유지한다. 중첩 그룹·맞춤 역할 언어·긴급 우회·개인 공간 공동 소유는 첫 구현의 복잡도에 추가하지 않는다. 기존 필수 그룹 제한·접근 요청·정제본 공개·운영 통제는 별도 구현/검증 과제로 계속 추적한다.
