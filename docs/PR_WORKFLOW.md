# PR 운영과 실수 기록

이 기준은 저장소의 사람과 개발 에이전트 모두에게 적용한다. 목표는 변경을 빨리 합치기 위해 검증을 생략하는 것이 아니라, 검토와 복구가 가능한 작은 단위로 지속 통합하는 것이다. 제품 요구사항이나 보안 불변식을 줄이지 않는다.

## 작은 기능 단위로 진행

1. 기능을 독립적으로 설명·검토·시험할 수 있는 단위로 나눈다. 여러 단위가 의존하면 기반 계약과 후속 연결을 순서대로 나누고, 부분 구현이나 비활성 경로를 완성 기능으로 표시하지 않는다.
2. 작업 중 단위가 준비되면 최신 `main`과 충돌 및 마이그레이션 순서를 확인하고 PR을 올린다. 새 기능을 계속 쌓느라 준비된 단위의 검토를 미루지 않는다. 큰 단위가 불가피하면 이유와 분리할 수 없는 의존성을 PR에 기록한다.
3. PR에는 범위·요구사항·실제 실행한 검사와 결과·미실행/미완료·위험 및 후속 작업을 적는다. 실제 모델·배포·품질을 확인하지 않았다면 확인했다고 쓰지 않는다.
4. 최종 커밋의 필수 CI와 변경에 필요한 회귀·보안 검사를 확인하고 충돌 및 중요 발견을 해결한 뒤, 사용자 또는 저장소 정책이 허용한 범위에서 머지한다. 실패·취소·대기는 통과가 아니다. 기존 변경이나 다른 작업을 버려서 충돌을 해결하지 않는다.
5. PR별로 병합 결과와 남은 작업을 전달한다. 사용자 승인이 필요한 저장소에서는 승인 전에 머지하거나 자동 머지를 예약하지 않는다.

### UI 변경 PR의 화면 증거

- 화면의 모양·동작·탐색에 변화가 있으면 PR 본문에 변경 화면의 캡처를 **반드시 포함**한다. 가능하면 같은 조건의 변경 전/후를 함께 보여 주고, 합성 데이터·화면 상태·뷰포트·검증 환경을 적는다. 캡처가 구현의 전체 기능이나 접근성 검증을 대신하지 않는다.
- 데스크톱 1440px과 모바일 390px에서 실제 브라우저로 확인한다. 변경 화면이 해당 크기에 적용되지 않으면 이유와 실제 확인한 크기를 기록한다. 캡처와 검증에 실제 계정·토큰·개인 정보·비공개 자료를 넣지 않는다.
- 환경·권한 문제로 캡처할 수 없다면 PR에서 사유와 미검증 상태를 명시하고 해결 또는 검토자의 명시적 예외 승인 전에는 UI 증거를 충족했다고 표시하지 않는다. 변경이 없는 PR은 화면 캡처를 요구하지 않는다.

## 모든 발견한 실수와 실패를 기록

- 작업 중 발견한 실수, 잘못된 가정, 실패한 테스트·검증·배포 시도와 사고 또는 아차사고를 [실수와 교훈 기록](MISTAKE_LOG.md)에 기록한다. 작은 실패는 같은 원인별로 묶어도 되지만 숨기지 않는다. 해결 전에도 `조사 중` 또는 `미해결`로 남기고, 나중에 같은 항목을 갱신한다.
- 각 항목에는 발생 시점·맥락·관찰된 사실과 영향·원인(확정/가설 구분)·조치·검증 근거와 결과·남은 일·관련 PR/이슈를 적는다. 사람을 탓하지 않고 재발을 막을 수 있는 조건과 절차를 적는다. 실패를 통과로, 미실행을 성공으로 표현하지 않는다.
- 실제 비밀값, 토큰, 개인 정보, 원문 자료, 내부 주소나 민감한 로그를 넣지 않는다. 공개 가능한 식별자와 안전한 요약을 사용하고, 공개하면 안 되는 세부 근거는 승인된 별도 경로에 보관한다. 기록 자체가 권한 확대나 정보 유출이 되지 않게 한다.
- 작업 기록은 해당 변경의 PR과 함께 갱신하되 긴급 대응으로 즉시 기록하기 어렵다면 후속 PR/이슈를 남긴다. 기록이 사건 대응이나 사용자 통지를 지연시키지 않는다. 원인과 예방 효과를 검증하지 않았다면 미확인으로 둔다.

## 기록 양식

```markdown
### YYYY-MM-DD — 짧은 제목
- 맥락/관련 PR:
- 사실과 영향:
- 원인: 확인된 사실과 미확인 가설을 구분
- 조치 및 재발 방지:
- 검증: 명령·결과 또는 미실행 이유
- 상태/후속 작업: 조사 중 / 수정 중 / 검증됨 / 미해결
```
