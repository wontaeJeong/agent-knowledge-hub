# 30,000 사용자 대비 용량 계획과 단계적 확장

> **상태: 설계/검증 계획. 성능 측정 결과나 30,000명 처리 보장이 아니다.**
> 출발점: [ADR 003](adr/003-single-cluster-initial-release.md)과 [K8S_RELEASE.md](K8S_RELEASE.md). 기존 OPS-011, NFR-001~010, JOB-001~012, SRH 및 SEC 요구사항을 유지한다.

## 1. 사용자 30,000명은 트래픽 수치가 아니다

§registered users = 30,000§만으로 App Pod 수, DB 크기, RPS를 정할 수 없다. **활성 사용자(DAU), 피크 동시 활성 세션, 초당 요청, 문서·근거 양, 검색 복잡도, 동시 에이전트 작업, 각 작업의 모델/검색/DB 호출 수**가 병목을 좌우한다. 사람의 화면 접속보다 에이전트의 지속 수집·질의·Lint가 부하와 비용을 더 크게 만들 수 있다.

아래는 **계산 방식의 예시**이며 실제 사용량 가정·예측이 아니다.

| 입력 | 예시 가정 |
| --- | --- |
| 등록 사용자 | 30,000명 |
| 일간 활성 비율 | 10% → DAU 3,000 |
| 피크 동시 활성 비율 | DAU의 5% → 150명 |
| 활성 1인당 요청 | 분당 2회 |
| 추정 외부 요청률 | §150 × 2 / 60 = 5 RPS§ |
| 요청당 내부 DB/검색 연산 | 10회라고 가정하면 약 50 연산/초 (DB query/s와 1:1은 아님) |

이 값은 평균보다 피크 시간대·에이전트 fan-out·대량 작업을 별도 모델링해야 한다. 등록 사용자 30,000명이어도 부하가 낮을 수 있고, 사용자 100명이 동시에 대규모 문서를 편입하면 단일 인스턴스를 압도할 수 있다.

### 수집해야 할 워크로드 데이터

- 사용자: 전체 등록·DAU/WAU·피크 동시 세션, 팀·공간별 요청, 사람/에이전트 호출 구분
- API: 엔드포인트별 RPS·동시 요청·p50/p95/p99 지연·오류/429·타임아웃
- 지식 데이터: 원본/페이지/버전/근거 수, 평균·p99 본문 크기, 첨부 저장량, 인덱스 크기·갱신량
- 작업: Ingest/Query/Lint 별 도착률, 동시 실행 수, 대기열 시간, 처리 시간, 재시도·중복률, 모델 토큰/비용
- DB: CPU·메모리·스토리지·IOPS·WAL, 잠금·슬로우 쿼리, 활성/대기 connection, 풀 포화
- 외부 의존성: SSO·원본·LiteLLM/vLLM 또는 승인된 모델 게이트웨이의 제한·오류·비용

## 2. 처음부터 지켜야 할 확장 호환성

초기에는 App x1 / PostgreSQL x1을 유지하되 **스케일아웃할 때 데이터 구조를 갈아엎지 않도록** 다음 원칙을 첫 서버 구현에 포함한다.

1. **Stateless App:** 요청 사이 진실의 원천은 DB/영속 저장소에 둔다. 세션은 서버 검증 가능한 토큰 또는 공유 세션 저장소로 설계한다. Pod의 로컬 디스크·인메모리 상태에 위키나 작업을 저장하지 않는다.
2. **발행 일관성:** PostgreSQL 트랜잭션, 승인 스냅샷·버전 비교, 멱등 키, 읽기와 쓰기의 권한 재확인. replica 수가 늘어나도 중복 발행하지 않는다.
3. **작업 내구성:** Ingest·Lint·인덱싱·모델 호출 등 장기 작업은 영속 작업 레코드, lease/heartbeat, retry/backoff 및 중지 정책으로 관리한다. 여러 worker가 같은 작업을 동시에 수행하지 않도록 설계한다. 큐/브로커 도입은 나중에 가능해야 한다.
4. **검색 파생 데이터:** 정본(원본·위키·버전)은 DB/오브젝트 저장소, 전문/벡터 인덱스는 재구축 가능한 파생 데이터다. 검색·캐시 응답 전에 서버에서 권한 확인.
5. **풀과 예산:** replica가 증가하면 §총 DB connections ≈ replica 수 × 프로세스/worker 수 × pool 크기 + 운영 여유§가 커진다. DB 허용 연결 수를 넘지 않도록 풀/동시 실행·요금·토큰 예산을 통제한다.
6. **배포 분리:** 스키마 마이그레이션은 각 App Pod 기동 시 중복 실행하지 않고 단일 배포 단계/Job으로 제어한다. 구성은 환경별, 이미지는 불변 버전으로 관리한다.
7. **관측 가능성:** 사용자 요청과 agent run → 비동기 작업 → 문서/발행까지 trace ID, 주체(개인정보 최소화), 비용·실패 원인을 연결한다.

## 3. 병목별 단계적 대응

| 관찰된 문제 | 우선 점검 | 후속 선택지(측정 후 결정) |
| --- | --- | --- |
| App CPU/메모리 포화, 읽기 p95 상승 | 비싼 동기 처리·쿼리·자원 제한 | stateless App replica 2+ 및 HPA/Ingress 분산 |
| 모델/자료 편입이 요청 처리 방해 | 동시 실행, 작업 대기·취소·중복 | worker Deployment 분리, 백프레셔, 큐/DB outbox |
| PostgreSQL 커넥션/잠금·IO 병목 | 연결 풀, 쿼리 계획, 인덱스·트랜잭션 | 풀 제한/풀러, 쿼리 최적화, 읽기 replica(읽기 적합 시) |
| DB 단일 장애·정기 유지보수 중단 | 가용성 목표·실제 복원 시간 | 오퍼레이터/관리형 PostgreSQL HA, failover 복구 시험 |
| 검색 인덱스가 DB 처리량 경합 | FTS/벡터 쿼리 비용·권한 필터 | 별도 검색 계층, 인덱스 갱신 worker; 정본은 DB 유지 |
| 외부 모델 호출 한도·비용 증가 | RPM/TPM, 동시 실행·시간/비용 | 모델 게이트웨이 단위 rate limit, 우선순위·예산 정책 |
| 클러스터 공동 장애가 서비스 목표를 위반 | 장애 도메인·RPO/RTO | 노드 분산·다른 장애 영역/클러스터 검토 |

**기능을 유지하는 수평 확장**과 **고가용성**은 다른 문제다. App 3개여도 단일 DB 장애는 해결되지 않는다. 반대로 DB HA가 있어도 느린 모델 호출은 해결되지 않는다.

## 4. 단계별 확장 로드맵

| 단계 | 구성 | 진입 조건과 완료 증거 |
| --- | --- | --- |
| S0: 1차 릴리즈 | 환경별 App 1 / PostgreSQL 1, 안전한 영속성·권한·백업·관측 | STG 실배포, 기능/보안/복원 확인. 다운타임 수용 명시 |
| S1: App 확장 | stateless App replica 2+, 필요 시 HPA | 피크 부하에서 API 포화·SLO 위반 확인, 다중 replica 동시성/세션 검증 |
| S2: 비동기 분리 | worker 1+, 영속 큐/lease, per-agent/tenant backpressure | 작업 적체·OOM·타임아웃 측정, 재시도/중복/취소/재처리 검증 |
| S3: 데이터 가용성·성능 | PostgreSQL HA/풀러·튜닝·필요 시 읽기 replica | DB 가용성 또는 쿼리/연결 병목 입증, failover/restore와 정합성 시험 |
| S4: 검색/장애 도메인 분리 | 별도 인덱스/검색, 필요 시 클러스터 분리 | 검색/DB 경합 또는 목표 RTO 위반 확인; 인덱스 재구축·ACL 회귀 검증 |

S1~S4는 반드시 순서대로 모두 실행해야 하는 체크리스트가 아니다. 장애/측정 결과에 따라 DB HA를 먼저 하거나, 단일 App으로 더 오래 운영할 수 있다. **유저 수 30,000명 도달은 자동 증설 스위치가 아니다.**

## 5. 성능 시험과 운영 전환 기준

1. **부하 모델:** 인증된 사람의 탐색·검색·읽기·발행과 에이전트 Ingest/Query/Lint를 별도 시나리오로 설계한다. 데이터셋에 사용자 30,000명과 현실적인 문서/ACL 분포를 생성하며, 스테이징/시험 환경에서 진행한다.
2. **시험 유형:** 정상·피크·스파이크·장시간(soak)·동시 승인/발행·DB 장애·모델 지연/실패·권한 철회와 대량 재색인을 시험한다.
3. **목표 수립:** 조직과 함께 엔드포인트별 p95, 오류율/가용성, 작업 완료 지연, 인덱스 신선도, RPO/RTO, 인당/작업당 토큰 비용을 **측정 가능한 수치로 승인**한다. 아직 값은 확정하지 않는다.
4. **증설 알림:** 앱 포화+p95 악화, DB 풀/잠금/IO 포화, 작업 대기시간 증가, 인덱스 지연, 모델 429/요금 급증을 지속 기간과 함께 경고한다. 예를 들어 '15분 이상 자원 사용률 70% 초과 + p95 악화'는 **초기 경보를 설계할 때의 예시**이지 테스트된 임계치가 아니다.
5. **증설 완료:** 개선 전후 같은 워크로드를 재시험한다. 처리량 증가뿐 아니라 지식 권한·근거·원자 발행·중복 방지·검색 최신성·복원 가능성도 회귀 검증한다.

## 6. 출시 후 관리 문서

성능 시험 결과와 환경별 실제 자원값, DB 크기, backup retention, RPO/RTO, 모델 비용, 알림 임계치는 새 운영 기록 또는 대시보드에 실측으로 업데이트한다. 이 문서는 추정/전환 원칙이고, 실제 처리량이나 SLO 보증값을 기입하지 않는다.
