# 메신저 대화 기록을 연결 지식으로 편입하는 계약

> **상태: 설계 제안 / 어댑터·UI·평가 미구현 (2026-10-30).** 일반 입력·영속 작업·권한·API는 [DATA_INGESTION.md](DATA_INGESTION.md), 역할은 [ACCESS_CONTROL.md](ACCESS_CONTROL.md), 결정은 [ADR 006](adr/006-web-first-data-ingestion.md)을 따른다. 여기의 대화와 결과는 합성 설계 예시이며 실제 실행 결과가 아니다.

## 1. 1주일 대화 입력의 기대 결과

사용자가 허용된 `2026-10-19~25` 대화를 웹에 넣고 기존 Redis 설정 위키와 함께 정리한다고 가정한다. 원본 타임존은 명시적으로 Asia/Seoul이며 아래 표시명은 인증된 회사 신원이 아니다.

| 원문 ID/시각 | 발언 예시 | 보존할 해석 |
| --- | --- | --- |
| m1 / 10-19 09:00 | 민수: “현재 v1.8.0의 TTL은 60초입니다.” | 특정 버전의 작성자 진술. 독립 설정/실행 증거는 아직 없음 |
| m2 / 10-21 10:00 | 민수: “다음 배포에서 TTL을 300초로 늘리는 건 어때요?” | 제안. 적용된 규칙이나 결정으로 쓰지 않음 |
| m3 / 10-22 14:00 | 지영: “스테이징 v1.8.1은 TTL 300초로 변경하기로 확정했습니다. 운영은 60초 유지입니다.” | 환경별 결정 기록 후보. 화자의 결정 권한/공식 채택은 별도 검토 |
| m4 / 10-23 15:00 | 민수: “스테이징 배포 완료됐어요.” | 완료 주장. 로그 없이 실행 검증 성공으로 표시하지 않음 |
| m5 / 10-25 16:00 | 수현: “스테이징에서 타임아웃이 늘었어요. 로그는 내일 첨부할게요.” | 반증/후속 검증 후보. 관측 환경·시점, 로그 미첨부 상태 유지 |

예상 변경안은 기존 Redis 설정 페이지의 환경/버전 조건 보완, 배포 판단 페이지의 제안→결정 맥락 연결, 장애/검증 과제 후보와 관련 근거 연결이다. 운영까지 TTL 300초로 바꾸거나 테스트 통과로 단정하면 실패다. 새 페이지가 꼭 필요한지 기존 문서와 비교하고, 단순 주간 요약은 탐색용 부가 결과일 뿐 지식 발전의 완료 조건이 아니다.

검토자는 각 변경에서 m1~m5의 원문과 앞뒤 발언·기간 밖 누락 문맥을 확인한다. 작성자가 본문을 수정해도 원본은 유지하며 선택된 입력/제안 해시가 바뀌면 재검토한다. 팀 발행은 기본 독립 사람 검토를 거치고 지식은 원본의 현재 권한을 넘지 않는다.

## 2. 정규화된 대화 레코드

| 필드군 | 최소 계약 |
| --- | --- |
| 원본 정체성 | source system/검증된 workspace ID, conversation ID, message ID를 **문자열**로 보존. 인증 주체와 업로더 ID는 따로 기록 |
| 발언/스레드 | 원문 텍스트·화자 ID/표시명·신원 매핑 검증 여부·thread/replyTo·순서·연결된 첨부 참조 |
| 시간 | 원문 시각 표현·알려진 타임존·정밀도·발생/수정/수집 시각. 누락은 unknown이며 업로드 시각으로 대체하지 않음 |
| 원본 anchor | RawBlob 버전·ZIP entry/파일 ID·행/JSON pointer/메시지 ID·내용 해시·가능한 byte 범위. 정규화 텍스트와 원문 위치의 매핑 |
| 수명주기 | 내용 revision·supersedes·명시 삭제/tombstone·관측 구간·export 완전성/제외 범위 |
| 접근 | 현재 원본 ACL 또는 unknown, 취급 등급·반출/모델 전송 정책·가공 계보·허용 독자 |

파서는 화자의 말과 인용·전달 메시지·코드 블록·시스템 이벤트를 구별한다. 반응/좋아요·“동의합니다” 반복 횟수로 사실의 독립 근거나 공식성을 높이지 않는다. 동일 표시명은 동일인, 동일 채널명은 동일 대화방이라는 증거가 아니다. 사용자 매핑도 인증된 관리자 매핑/실제 원본 ID와 구별해 신뢰 수준을 기록한다.

원문을 줄바꿈/인코딩 정규화해도 근거로 돌아갈 수 있어야 한다. TXT의 멀티라인 본문, 한국어 날짜/오전·오후, 이모지·코드·첨부 안내, CSV 따옴표/행바꿈을 지원 fixture로 고정한다. 인코딩이 불명확하면 샘플과 선택지를 보여주고 조용히 깨진 텍스트로 진행하지 않는다. 상대 날짜는 발언 시각과 원본 타임존이 있을 때만 해석하며 “내일 로그”를 로그가 실제 생긴 날로 바꾸지 않는다.

## 3. 스레드·기간·누락

사용자가 1주일을 선택하면 **선택된 발언 범위**와 그 해석에 사용한 **문맥 범위**를 따로 표시한다. 기간 밖 부모/답글이 파일에 있으면 사용자에게 포함 목적을 설명하고 선택 범위에 고정한다. 파일에 없다면 `missing_parent / missing_replies / missing_attachment`를 기록하며, 메신저 전체에 접근했다고 가정해 자동 수집하지 않는다.

메시지 경계/스레드를 보존해 청크를 만들고 긴 스레드는 관련 앞뒤 문맥과 anchor를 유지해 나눈다. 사건 단위 후보를 합친 뒤 다른 날의 정정·조건·반증을 다시 검사한다. 선택 밖 자료를 모델 문맥으로 슬쩍 포함하거나 마지막 날의 결론만 남겨 실패·기각 이유를 삭제하지 않는다. 날짜·출처가 없는 붙여넣기는 출처 제한이 있는 일반 텍스트로 표시하며 메신저 식별자/시간을 생성하지 않는다.

## 4. 중복·수정·삭제와 증거 독립성

검증된 원본 namespace+대화 ID+message ID가 있고 내용 hash가 같으면 동일 관측을 재사용한다. 같은 ID의 다른 내용/수정 시각은 새 SourceRevision으로 추가하고 기존 후보·페이지 영향 분석을 만든다. 순서가 뒤바뀌거나 m2가 다른 export에도 등장해도 여러 독립 근거로 계산하지 않는다. 내보내기 시각이 더 최신이라는 사실만으로 메시지 내용을 우선 확정하지 않는다.

신뢰 가능한 message ID가 없으면 원본 파일/항목 위치+내용 hash로 **그 파일의 재전송**을 식별한다. 서로 겹치는 TXT export는 보수적인 중복 후보로 제시하고 확정 매핑 없이 자동 병합하지 않는다. 같은 사람이 같은 문장을 실제 두 번 보낸 것은 두 사건일 수 있으므로 본문 hash만으로 전역 삭제하지 않는다.

명시적 삭제/철회 이벤트가 있을 때 새 tombstone과 파생 영향 처리를 기록한다. 후속 export에서 메시지가 보이지 않는 것만으로 삭제라고 간주하지 않는다. 파일 누락·기간 변경·export 권한 차이일 수도 있다. 수동 업로드만으로 외부 메신저의 실시간 수정/삭제/ACL 회수를 알 수 없으며, 신선도 기한이 지난 제한 원본은 원래 ACL 정책에 따라 차단/재확인한다. 지속 동기화를 지원하려면 별도 공식 API 커넥터와 실제 철회 회귀가 필요하다.

## 5. 첫 구조화 어댑터 후보: Slack export

Slack 공식 내보내기에는 메시지 JSON과 파일 **링크**가 포함될 수 있다. 내보내기 범위/가능 기능은 서비스의 권한·플랜/정책에 따라 다르며 이 제품이 export 권한을 제공하지 않는다. 첫 어댑터는 익명화한 실제 지원 형식 fixture를 확보해 판별 규칙·지원 형식/버전을 고정한 뒤 활성화한다. 후보라는 이유로 Slack 연결/운영 호환을 지원 목록에 올리지 않는다.

- 채널/날짜별 파일, 사용자/대화 메타데이터, `ts`/`thread_ts`의 관계를 읽되 식별자를 부동소수점 숫자로 바꾸지 않는다.
- 모든 thread 답글/첨부/수정 이력이 포함됐다고 가정하지 않는다. `files`/링크 참조는 증거 본문 확보와 구별하고 누락을 표시한다.
- private/DM/외부 협업 대화는 별도 입력 접근 증거와 취급 정책이 필요하다. public 채널이라는 문자열만으로 회사 전체 지식 독자를 허용하지 않는다.
- TXT/KakaoTalk/Teams/다른 사내 메신저는 각각 형식/버전 fixture·인코딩·날짜/신원/누락 계약을 검증해야 한다. Slack 파서를 이름만 바꿔 호환이라고 표시하지 않는다.

## 6. 검토·평가와 근거

[DI-05~18/24](DATA_INGESTION.md)의 파싱·맥락·중복·권한·의미 품질 회귀와, [평가 계약](EVALUATION.md)의 고정 정답셋/대조 조건을 따른다. 정답에 포함된 결정·제안·조건·실패·누락을 얼마나 보존했는지와 기존 위키의 근거 있는 변화·불필요 변경을 측정한다. 아직 fixture/파서 구현·실제 모델 실행·사용자 검토 시간 측정·지원 브라우저/OS 시험은 하지 않았다.

2026-10-30에 확인한 공식 형식 참고:

- [Export your workspace data](https://slack.com/help/articles/201658943-Export-your-workspace-data): 내보내기는 Slack 자체 권한/정책과 선택 범위를 따른다.
