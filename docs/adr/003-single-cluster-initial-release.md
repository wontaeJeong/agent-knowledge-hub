# ADR 003: 동일 Kubernetes 클러스터에서 STG/PROD를 분리하고 단일 인스턴스로 시작한다

- 날짜: 2026-10-29
- 상태: **채택(1차 릴리즈의 목표 설계)**. 구현·검증·배포 완료를 뜻하지 않는다.
- 적용 범위: agent-knowledge-hub의 첫 사내 서비스 릴리즈. 현재 0.2 로컬 데모에는 서버 DB/SSO/K8s 매니페스트가 없다.
- 참조: [초기 Kubernetes 배포 설계](../K8S_RELEASE.md), [용량·확장 계획](../SCALING_PLAN.md)

## 결정

하나의 기존 Kubernetes 클러스터에 정확히 두 네임스페이스를 사용한다.

- §agent-knowledge-hub-stg§: 스테이징
- §agent-knowledge-hub-prod§: 운영

각 환경은 처음에 **애플리케이션 replica 1, PostgreSQL 인스턴스 1**로 구성한다. 애플리케이션과 DB는 **서로 다른 워크로드/Pod**이며, 각 환경의 DB·PVC·자격증명·설정·권한·백업을 분리한다. 동일한 소스/이미지로 배포하되 환경별 설정과 데이터는 공유하지 않는다.

초기 릴리즈에서 다중 애플리케이션 replica, DB HA, 오토스케일링, 읽기 복제본, 전용 검색 클러스터, 다중 클러스터 DR은 도입하지 않는다. **성능 최적화를 미루는 것이 데이터 영속성·권한·백업·복구·관측 및 정확성 검증을 미루는 근거가 되지 않는다.**

## 이유

- 소규모 초기 사용량이 확인되지 않은 상태에서 운영 복잡도를 줄인다.
- STG와 PROD의 데이터 및 자격증명을 별도 소유·백업·복원한다.
- 향후 무중단 서비스·대규모 사용자가 필요하면 애플리케이션, 작업자, DB를 단계적으로 확장한다.
- 가입자 30,000명 자체는 병목의 충분한 증거가 아니다. DAU, 피크 동시 요청, 에이전트 실행 수, 자료/인덱스 크기, 모델 호출 패턴을 측정해 판단한다.

## 받아들이는 제약과 위험

- 앱 1개/DB 1개이므로 Pod 재시작·노드 장애·배포 시 읽기/쓰기 중단이 발생할 수 있다. **HA/SLA 보장 없음**.
- 한 클러스터를 공유하므로 클러스터 전체 장애나 공유 스토리지·노드 장애는 두 환경에 동시에 영향을 줄 수 있다.
- Kubernetes 네임스페이스만으로 통신·리소스·권한 격리가 완성되지 않는다. RBAC, ResourceQuota, NetworkPolicy, Secret, 계정 및 백업 권한을 별도로 강제한다.
- DB PVC만으로는 백업이 되지 않는다. 복구 가능한 외부 사본과 복원 점검이 필요하다.
- 동시 작업과 다중 사용자 발행은 앱 replica가 하나여도 DB 트랜잭션·멱등성·버전 충돌 방지가 필요하다.
- 현재 §Dockerfile§/§compose.yaml§은 정적 Vite 데모를 제공하며, 현 시점에는 서버 데이터 저장소가 없다. 이것을 그대로 사내 다중 사용자 운영 배포로 간주하지 않는다.

## 전환 조건

[용량·확장 계획](../SCALING_PLAN.md)의 측정 기준에 따라 애플리케이션 스케일아웃, 분리 작업자, DB HA, 검색 분리를 **필요한 순서**로 수행한다. 네임스페이스의 용도와 데이터 소유 경계는 전환 중에도 유지한다. 가용성 요구가 높아지면 30,000명 도달 이전에 HA를 우선할 수 있다.

## 대안과 미채택

- **초기부터 STG/PROD 별도 클러스터:** 장애 격리는 개선되지만 현 단계의 추가 운영 부담을 정당화할 요구가 없다. 엄격한 정책·서비스 중요도에 따라 재검토한다.
- **초기부터 다중 replica + DB HA:** 가용성에는 유리하지만 아직 실제 트래픽/운영 목표가 없다. 추후 단계에서 검토한다.
- **동일한 DB에 STG/PROD 스키마만 분리:** 테스트·권한·실수의 영향이 운영 데이터에 번질 수 있어 채택하지 않는다.
