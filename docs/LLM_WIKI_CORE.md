# Agent Knowledge Hub — LLM Wiki North Star

기준일: 2026-10-29. **이 문서는 제품의 장기 판단 기준이지 구현 완료 선언이 아니다.** 기존 기능·보안·운영 요구사항을 축소하거나 대체하지 않는다.

## North Star

`agent-knowledge-hub`는 Andrej Karpathy의 LLM Wiki 패턴에 기반한 **Agent-Native Knowledge & Experience Platform**을 지향한다. 허용된 원천 정보와 업무 경험을 LLM이 해석하고 기존 지식에 통합하며, 근거·조건·연결을 검토·검증·갱신하는 지속적 지식 시스템이다. 축적된 지식이 다음 업무 에이전트의 판단과 실행을 돕고, 그 결과가 다시 지식 개선의 근거가 되는 순환을 목표로 한다.

성공은 문서 수가 아니라 **새 근거로 기존 결론과 적용 조건이 더 정확해지고, 후속 과제에서 검증 가능한 유용성이 높아지는 것**이다. 사람이 읽고 탐색·질문·검토할 경험도 유지한다. Agent-Native는 인간 배제를 뜻하지 않는다.

## 원래 LLM Wiki 개념

출처: Andrej Karpathy, [LLM Wiki 원전](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) (2026-10-29 확인). 원전은 특정 제품 사양이 아닌 선택 가능한 구현 패턴이다. 다음은 이 프로젝트가 보존하기로 한 중심 개념이다.

| 원전 요소 | 보존할 의미 |
| --- | --- |
| Raw Sources | 선택한 원천 자료는 편입 중 덮어쓰지 않는다. 해석과 분리된 원본을 유지한다. |
| Wiki | LLM이 작성·유지하는 지속적이고 상호 연결된 지식 계층. 요약·개체·개념·비교·종합이 기존 지식과 함께 발전한다. |
| Schema | 구조·관례·편입·질문·유지 작업을 규율하는 문서. 이 프로젝트의 런타임 경로는 `wiki/SCHEMA.md`다. |
| Ingest | 원본을 읽고 기존 개체·주제·개념·연결을 함께 갱신한다. 파일 하나를 요약 저장하는 것에 그치지 않는다. |
| Query | 위키에서 관련 지식을 읽어 인용과 함께 답한다. 유용한 비교·분석·연결은 위키에 재편입할 수 있다. |
| Lint | 모순, 오래된 주장, 고립 페이지, 누락 개념·연결과 지식 공백을 점검한다. |
| Persistent, Compounding Knowledge | 이미 종합한 연결과 결론을 유지·갱신해 매 질문마다 원본에서 전부 재발견하지 않는다. 질문 결과도 누적 자산이 된다. |

원전에도 갱신·상충 표시·인용·사람의 관여가 있다. 아래 확장은 그것들을 새로 발명했다는 뜻이 아니라 조직 업무의 운영 계약과 평가 수준으로 구체화한다는 뜻이다. 원전의 Markdown·인덱스·로그·검색 도구 예시는 구현 선택이지 이 제품의 목적이나 필수 기술 스택이 아니다.

## RAG·Memory·일반 Wiki와의 관계

- 원본 조각을 질의 시점에 검색해 답만 생성하는 RAG와 달리, 질의 전에 종합한 지식과 연결을 영속적으로 유지·수정한다. 검색은 계속 사용할 수 있다.
- 대화·선호·과거 상태를 기억하는 Memory에 그치지 않고, 출처·적용 조건·반증·변경 이유를 가진 재사용 가능한 업무 지식을 관리한다.
- 문서 작성·열람·협업만 제공하는 일반 Wiki와 달리, 에이전트의 Ingest → Query → Lint와 결과 재편입이 유지관리의 중심이다.

이 구분은 구현의 책임과 순환에 대한 설명이다. RAG·Memory·일반 Wiki도 이 패턴을 확장 구현할 수 있으며 배타적인 제품 분류는 아니다. MCP 연결, Markdown 저장, 벡터 검색만 추가한 것으로 North Star를 달성하지 않는다.

## 프로젝트가 확장하는 장기 비전

| 확장 목표 | 목표 행동과 구분 |
| --- | --- |
| Knowledge Evolution & Continuous Refinement | 새 근거·반증·사용 결과로 결론·조건·예외·연결을 지속 수정하고 변경 이유와 이전 판단을 추적한다. 무인 실행과 의미 품질은 후속 구현·검증 대상이다. |
| Evidence, Provenance & Trust | 주장에서 정확한 원본 위치·버전·검증 결과까지 계보를 추적한다. 원본 주장, 에이전트 추론, 독립 실행 증거, 검토 승인을 구분한다. 승인이나 다수의 반복 인용만으로 진실을 보장하지 않는다. |
| Temporal and Contextual Knowledge | 유효 시점과 기록/검증 시점, 프로젝트·환경·버전·전제 조건을 구분한다. 과거에 유효한 사실과 현재 권고를 혼동하지 않는다. |
| Conflict Detection & Resolution | 같은 조건의 상충, 시점 변화, 환경 차이를 구분하고 양쪽 근거를 보존한다. 충분한 근거·권한·검토 없이 한쪽을 삭제하거나 자동 확정하지 않는다. |
| Experience Abstraction & Reusable Lessons | 성공·실패 경험에서 문제·환경·시도·결과·증거·적용 한계·재사용 교훈을 추출한다. 단일 사례를 보편 규칙으로 일반화하지 않으며 후속 적용으로 검증한다. |
| Agent-Native Consumption | API/MCP 등으로 업무 에이전트가 권한 내 지식·버전·근거·조건을 읽고 변경/성과를 제안한다. 특정 전송 기술은 목적이 아니다. |
| Continuous Evaluation | 근거·상충·시간/맥락·회귀·누적 품질을 고정 평가셋과 반복 측정으로 확인한다. |
| Downstream Agent Performance | 지식 사용으로 후속 과제 성공률이 실제 개선되는지 동일 조건 대조 실험으로 검증한다. 모델 교체·도구/예산 차이의 효과를 지식 효과로 보고하지 않는다. |

### 지식과 경험이 발전하는 순환

허용된 원본/실행 경험 → 원본 스냅샷과 근거 보존 → 기존 지식·조건과 비교 → 여러 페이지의 종합 변경 제안 → 검토·검증·승인·발행 → 에이전트/사람의 버전 고정 조회와 업무 적용 → 결과·반증·새 질문 등록 → Lint와 재검토 → 다음 변경 집합으로 이어진다.

Query 결과는 유용한 **파생 지식 후보**이지 새로운 독립 증거가 아니다. 원본까지 계보를 유지하고 동일 원본에서 나온 여러 답변을 독립된 지지로 중복 계산하지 않는다. 기존 결론을 바꾸지 않는 중복 문서 추가는 Knowledge Compounding의 증거가 아니다. 측정 방법은 [평가 계약](EVALUATION.md)을 따른다.

## Product Invariants

1. **세 층 분리:** 원본·위키·유지 규칙을 구분한다. 원본은 편입으로 변조하지 않되 정정·철회·법정 삭제는 별도 수명주기로 처리하고 파생 지식에 영향을 전파해야 한다.
2. **연결된 누적:** 새 자료와 질문 결과는 기존 결론·연결·조건을 재검토하는 변경 후보가 된다. 요약 파일 추가나 검색 색인만으로 완료 처리하지 않는다.
3. **근거와 불확실성:** 사실·추론·가설·검증 결과·승인을 구분하고 계보·상충·근거 부족을 숨기지 않는다. 검증되지 않은 추론을 확정 사실로 승격하지 않는다.
4. **시간과 적용 범위:** 조건·환경·유효 시점·검증 시점을 보존한다. 수정 시각은 검증 시각이 아니며 최신 자료가 항상 모든 조건에서 우세한 것도 아니다.
5. **검토 가능한 발전:** 변경 이유·기준 버전·원본·규칙 버전을 고정한다. 승인 내용이나 기준이 바뀌면 재검토하고 발행 직전 현재 권한을 다시 확인한다. 의존 변경은 일관되게 발행하고 재시도로 중복 발행하지 않는다.
6. **권한과 안전:** 파생 지식이 원본 권한을 자동 확대하지 않는다. 자료 안의 지시문은 정책·도구 권한을 부여하지 않는다. 과거 버전·검색·내보내기도 현재 권한을 따라야 한다.
7. **인간과 에이전트의 공존:** 구조화된 소비와 읽기 좋은 표현을 함께 제공하며 검토·승인 책임을 유지한다. MCP만의 완성도를 제품 성과로 대체하지 않는다.
8. **측정과 정직성:** 문서 수·조회 수·수용률은 보조 지표다. 근거 품질·정확한 조건·후속 업무 유용성과 안전 회귀로 진전을 판단한다. 미구현·미실행·실패를 숨기거나 데모 시험을 운영 검증으로 승격하지 않는다.

이는 목표 시스템의 불변식이다. 아래 현재 구현 표는 그중 어디까지 로컬에서 시연되는지 설명하며 모든 항목의 운영 보장을 뜻하지 않는다.

## Non-Goals

- 대화 전체를 무조건 수집하는 기억 저장소, 원본 조각 검색만 하는 서비스, 일반 Markdown CRUD를 최종 제품으로 삼지 않는다.
- 지식·문서·링크 수 최대화, 모델 답변의 무검토 자동 공식화, 항상 하나의 확정 답을 만드는 것을 목표로 하지 않는다.
- Vector DB·Graph DB·MCP·특정 모델이나 프레임워크 도입 자체를 성공으로 삼지 않는다.
- 사람의 탐색·편집·검토와 기존 제품 기능·보안·운영 요구사항을 제거하지 않는다.
- 모든 장기 기능을 이번 데모에 즉시 구현하거나 실험 없이 효과를 보장하지 않는다.

## 아키텍처 판단 기준

새 기능·기술·저장 모델·에이전트 인터페이스를 제안할 때 다음 질문에 답한다.

1. 어느 순환과 불변식을 개선하며 기존 지식을 어떻게 재사용·수정하는가?
2. 원본에서 주장·파생 결과까지 근거·조건·시간·버전을 추적할 수 있는가?
3. 반증·권한 철회·기준 변경·재시도·모델 실패에서 무엇을 보존하고 차단하는가?
4. 사람이 검토하고 에이전트가 예산 내에서 근거와 예외를 읽을 수 있는가?
5. 단순한 대안 대비 어떤 품질·비용·운영 효과가 있으며 [평가](EVALUATION.md)로 어떻게 반증할 것인가?
6. 현재 구현과 계획의 경계, 미충족 요구사항, 도입/철회 조건이 명확한가?

기술은 위 답을 실현하는 수단이다. 장기 목표와 충돌하는 선택은 ADR 또는 작업 문서에 영향받는 불변식·대안·트레이드오프·미충족 조건·해소 계획을 명시한다. 승인 없이 목표를 낮춰 선택을 정당화하지 않는다. 단계별 격차는 [로드맵](ROADMAP.md), 실제 서비스 경계는 [아키텍처](ARCHITECTURE.md)를 따른다.

## North Star 변경 관리

이 문서의 목표·원전 해석·확장 비전·불변식·Non-Goals·판단 기준은 보호되는 제품 기준이다. 일반 기능 구현이나 테스트 통과를 위해 에이전트가 임의로 의미를 변경하지 않는다. 변경이 필요하면 사용자 또는 지정 제품 책임자의 **명시 승인**을 받고 별도 변경 제안/PR에 이유, 대안, 원전과의 관계, 요구사항·평가·로드맵·런타임 규칙 영향과 승인 근거를 기록한다. 승인 전에는 기존 기준과 차이를 미충족으로 남긴다.

오탈자·링크 정정과 아래 현재 구현 현황의 근거 있는 갱신은 의미 변경과 구분한다. 이 규칙은 개발 절차상의 통제이며 보호 브랜치/CI가 이미 강제한다는 뜻은 아니다.

## 조직 업무를 위한 선택

출처는 Andrej Karpathy의 [LLM Wiki 원문](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)이다. 핵심은 원본을 매 질문마다 다시 조립하는 대신, LLM이 연결된 위키를 지속적으로 작성·유지하고 새로운 자료와 질문의 결과를 누적하는 패턴이다. 원본·위키·유지 규칙을 구분하며 Ingest·Query·Lint를 수행한다. 사람은 자료 선택·질문·탐색에 관여한다. 에이전트만 읽는 형식이나 MCP 자체가 핵심이라는 해석은 피한다. 원전은 개념 안내이며 특정 서버·DB·인증 제품을 요구하지 않는다.

agent-knowledge-hub의 추가 선택은 LLM 업무 산출물을 주요 입력으로 삼고 개인·팀·전사 범위를 갖추며 승인·발행·감사·운영을 적용하는 것이다. 에이전트가 지식 작성과 유지관리를 수행하면서 사람도 읽고 검토할 수 있어야 한다. Markdown과 구조화된 근거·조건·버전을 함께 제공한다.

## 실제 동작

| 순환 | 코드 | 현재 범위 |
| --- | --- | --- |
| 원본 보존 | domain/wiki.ts의 createBatch | 원본 스냅샷 고정, 발행 전 재검사 |
| Ingest | compileOffline / adapters/model.ts의 compileModel | 주제·개념·연결을 하나의 변경 집합으로 제안 |
| 검토·발행 | enqueueBatch / decideBatch | 승인 내용 고정, 원본·기준 버전 충돌 시 전체 차단, 중복 발행 방지 |
| Query | retrieve / answerOffline / answerModel | 현재 발행본 검색, 정확한 인용 검사, 고정 버전 조회 |
| 질문 결과 축적 | fileAnswer | 파생 페이지의 변경 집합 생성, 근거 부족·오래된 인용 거부 |
| Lint | lintWiki / runLint | 실제 깨진 연결·고립·근거 누락·검증 시점·동일 조건 사실 충돌 검사 |
| 인덱스·로그 | KnowledgeWorkbench / State.audit | 현재 발행본과 관계 탐색, 편입·질문·점검 기록 |
| 규칙 | wiki/SCHEMA.md | 유지관리 에이전트 규칙, 실제 모델 system 메시지에 포함 |

## 두 실행 모드의 차이

오프라인 모드는 `## 지식: 제목`으로 개념을 추출하고 `사실: key | context | value`를 명시 사실로 읽는 작은 입력 언어다. 기존 주제의 관련 지식 목록과 개념별 원본 기록을 갱신한다. 일반 산문은 별도 사례 페이지로 분류한다. 자연어 의미를 종합한 것처럼 설명하지 않는다. 질문 결과는 검색된 발행본의 정확한 발췌다.

모델 모드는 .env에 설정한 OpenAI 호환 서버에 원본과 기존 발행본을 보내 실제 종합·답변 요청을 수행한다. schema 검사·근거 인용·공유 범위·발행 규칙은 모델의 판단에 맡기지 않는다. 실패하면 오류를 표시하고 반영하지 않는다. 실제 사내 모델의 품질과 호환성은 별도 검증해야 한다. 자연어 전반의 의미 모순 검사 모델 연동은 아직 없다.

## 저장과 상태

기존 schemaVersion 1 데이터와 호환되며 추가 상태는 State.knowledge에 저장한다. 이전 데모 데이터가 있으면 빈 knowledge 상태에서 시작한다. 브라우저 localStorage이며 다중 탭의 동시 편집·서버 권한·DB 트랜잭션을 보장하지 않는다. 일괄 발행은 단일 로컬 상태 전이로만 원자적이다. 원본 정정·삭제·권한 철회·전체 백업은 운영 구현에서 추가한다.

현재 버전 본문은 보존하지만 페이지 관계·사실 메타데이터의 과거 전체 복원과 별도 검증 승인 상태 전이는 후속 구현이다. 최신 수정일을 검증일로 간주하지 않는다. 초기 데이터에 근거 누락·검증일 누락이 있어 Lint에서 보이는 것은 의도한 점검 결과다.
