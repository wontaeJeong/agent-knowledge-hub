# Task 11 — 개별 자료 삭제와 이력 정리

요구사항: LIF-005, VER-012. 기준 계획은 `docs/superpowers/plans/2026-11-16-remaining-roadmap.md` Task 11이다. 기존 공간/원본/페이지 계보 삭제와 초안·이전 발행 버전·원본 스냅샷 보존을 새 기능으로 다시 표시하지 않는다. 이 문서는 코드 연결과 합성 시험의 범위를 설명하며 전체 요구사항의 운영 수용 완료 선언이 아니다.

## 정적 대조와 선택한 범위

기존 `ContentRetentionService`는 미참조 초안, 비최신 발행 버전, 비최신 원본 스냅샷을 정리한다. `runtimeResults`는 불변 이력 차단으로 남았고 `AttachmentWorkflow`는 슬롯·불변 버전·철회·검토 연결을 제공하지만 개별 과거 파일의 영구 정리는 없었다. 기존 `operations/erasure.ts`의 선택 루트는 source/page이며 이것을 임의 주체 전체 삭제로 넓히지 않았다.

| 이번에 개별 선택하는 유형 | 실제 효과 | 보존/차단 |
| --- | --- | --- |
| `attachment-version` | 정확한 슬롯/리비전/파일 ID의 과거 버전과 파일 메타데이터 삭제. 슬롯과 현재 파일 유지 | 현재 head, 스냅샷/검토 연결/가져오기 아카이브/다른 CAS 참조, 다운로드 권한, 고정 공유 계보, 현재·과거 원본 상한, 법적 보존 |
| `runtime-answer` | 작성자가 식별되는 정확한 저장 답변 삭제 | 질문·재편입·주장·근거·성과 등 참조, 불명확한 입력 계보, 현재·고정 버전 및 과거 원본 접근 |
| `runtime-job` | 작성자가 식별되는 정확한 종료 실행 이력 삭제 | 실행 중 작업, 보존 답변에 연결된 결과, 파생/불명 참조. 답변을 함께 선택하면 두 유형을 같은 승인 집합에서 정리 |

현재 Lint 저장소는 주체별 최신 결과 하나이며 별도의 불변 이력으로 가장하지 않는다. 질문 스레드, 정련의 append-only 주장/근거/성과, 가져오기 아카이브, 내보내기 보관본, 검색 색인, 원본/발행본은 이 API의 개별 삭제 유형으로 승격하지 않았다. 이들은 참조 그래프에 남아 정리를 차단하며 원래 법정 삭제·보존 경로를 유지한다. LIF-005의 모든 외부 캐시·백업 사본 삭제와 VER-012 전체 운영 수용은 별도 조건이다.

## 수동 선택·독립 승인 계약

`/api/v1/retention/pruning`의 GET은 현재 접근 가능한 개별 대상과 검토 요청을 반환한다. POST 하위 경로는 `/preview`, `/plans`, `/review`, `/execute`이다. 개인 식별자·역할·SQL·경로·파일 해시는 요청자가 주입하지 않는다. selection은 위 세 가지 엄격한 DTO이며 한 요청은 중복 없는 최대 100건이다. 목록은 최대 100건, 화면의 대상은 25건 단위이며 더 많은 대상은 알려진 식별자로 같은 API에서 선택할 수 있다. 제품 그래프 10,000행과 공통 저장 그래프 100,000행 한도를 넘으면 닫힌다. 큰 공간의 전체 목록 탐색/점진적 처리는 후속 조건이다.

공간 Owner가 미리보기 해시와 현재 보존 정책 revision으로 계획을 만들고, 요청자 및 선택 자료의 작성자와 다른 현재 Admin이 같은 해시를 검토한다. 검토자는 화면에서 현재 참조와 해시 일치를 확인한 뒤 승인한다. 계획은 30분 동안 유효하며 자동 실행·기본 삭제 기간은 추가하지 않는다. 기존 설정에 유한한 보존 기간이 있으면 수동 선택도 그 최소 기간을 줄이지 못한다. 첨부는 부모가 source이면 sourceVersions, page이면 publishedVersions, 답변/실행은 runtimeResults 기간을 적용한다. 필요한 시각이 없으면 차단한다. null은 자동 기간 미설정이고 수동 삭제는 이 별도 승인으로만 허용한다. 법적 보존 해제 권한을 계획으로 대체하지 않는다.

독점 mutation gate 아래에서 제품/저장 참조·현재 ACL·보존 정책·법적 보류·고정 공유·내용 지문을 다시 계산한다. 승인자 현재 역할과 요청자/승인자의 현재·과거 페이지 및 전이적 원본 접근을 실행 직전 재검사한다. 내용·참조·정책이 바뀌면 새 계획/승인이 필요하다. 성공 재시도는 현재 권한을 확인한 후 기존 영수증을 반환하며 중복 삭제를 만들지 않는다. 실패한 실행은 롤백하고 본문 없는 실패 영수증을 남긴다.

`content_retention_plans`는 새 typed graph 대상으로 분류하고 SQL-visible 컬럼·타입·nullable 계약을 고정했다. 새 본문 컬럼이나 미분류 테이블/FK는 기존 fail-closed inventory를 통과하지 못한다. 계획 자체는 삭제 의도/승인 기록이며 독립 제품 근거로 취급하지 않는다. 계획의 selection/영수증은 임의 JSON이나 원문을 저장하지 않는다. 비본문 메타데이터와 ID만 노출하며 기존 private projection을 유지한다. 본문 안의 정확한 ID/해시 참조 검사는 PostgreSQL 안에서 수행한다. 계보가 불명확한 비공개 콘텐츠가 있으면 보수적으로 차단하므로 실제 공간의 정리 가능 비율을 보장하지 않는다.

## DB 삭제·물리 정리·복구

정확한 artifact tombstone과 제품 행 삭제, 실행 영수증 및 계획 상태 전이를 같은 트랜잭션에 기록한다. 첨부 파일은 CAS 물리 정리 전까지 `blocked / PHYSICAL_BLOB_PURGE_REQUIRED`다. 기존 `OperationsService.purgeApprovedBlobs`의 명시적 호스트 경로만 커밋된 tombstone에서 파일 해시를 가져오며, 독점 gate 아래 다른 live 참조가 없는 파일만 제거한다. 실제 제거 adapter가 완료한 해시 집합으로만 개별 정리 영수증과 idempotent 계획 영수증을 완료로 바꾼다. 다른 자료의 head나 공유 CAS 파일을 지우지 않는다. 외부 백업/내보내기/브라우저 사본까지 삭제했다고 주장하지 않고 `allCopiesErased=false`를 유지한다.

새 artifact 유형은 기존 독립 암호화·서명 복구 원장의 `erasedArtifacts`에 포함된다. 격리 복원은 독점 gate에서 새 유형을 재생하고 현재 법적 보존·공유·참조·head와 충돌하면 격리 해제를 막는다. INSERT/UPDATE DB trigger는 삭제된 답변/실행 ID와 과거 첨부 리비전/파일 ID의 재생성을 막는다. 원장의 알려진 삭제를 unknown reference 우회 근거로 사용하지 않는다. 대량 복구가 100개 granular 후보를 넘으면 현재 경로는 차단하며 분할/운영 복구 인수가 필요하다.

## 검증과 현재 한계

- Node 24에서 전체 `npm run check`: 소스/스크립트·가져오기·평가·251개 요구사항·서버 타입·빌드·정적 HTTP smoke. 기존 큰 번들 경고는 남았다.
- 새 PostgreSQL 회귀 21개: 실제 삭제/현재 head 보존/다른 작성자 보존, 독립 승인/권한 철회/정책 변경, 공유·법적 보존·스냅샷·다운로드·불명 참조, 실제 합성 CAS 파일 제거/영수증, signed ledger 복원 및 현재 hold 충돌, DB 재생성 fence, 기존 최소 기간 보호.
- 별도 실제 OIDC UserInfo·세션·CSRF HTTP 시험 1개가 인증/독립 검토/실행/typed DB 효과와 미인증·CSRF·철회를 확인한다. 전체 retention과 erasure/복구 격리/저장 그래프/첨부 lifecycle 회귀도 실행했다.
- 실제 Chromium 1440×1100, 390×1000의 현재 개별 선택/미리보기 화면을 [증거](../pr-assets/granular-retention/README.md)에 남겼다. 모바일 가로 넘침은 없었다. 브라우저 fixture만 pool 24이며 운영 리소스/기본 pool은 변경하지 않았다. 기준 통합 브랜치의 알려진 전체 App 동시 인증 bootstrap 문제는 pool 6에서 재현됐고 pool 24 재시도에서도 간헐적으로 나타났다. PR 54의 독립 인증 수정과 조합한 최종 전체 App 인수는 별도다. 순차 native HTTP 시험은 기본 fixture pool 6에서 통과했다.

North Star의 원본/파생/근거 분리, 현재 권한과 기준 버전, 검토 및 복구 불변식 1·3·5·6·8을 보강한다. 기존 지식의 독립 근거를 보존하며 쓸모없는 과거 사본만 명시적으로 정리한다. 삭제 건수·저장 비용 감소를 지식 품질이나 후속 에이전트 성능 향상으로 바꾸지 않는다. 단순 TTL보다 보수적 수동 검토를 택했으며 효과/성능 주장은 평가 계약의 대조 실험 전까지 목표다. 1 node·1 app Pod·1 DB의 초기 최소 구성에 새 서비스나 daemon을 추가하지 않는다.
