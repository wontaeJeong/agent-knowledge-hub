# 실수와 교훈 기록

### 2026-10-31 — 버전 워크플로 삭제 누락
- 원인과 영향: 삭제 인벤토리가 버전 메타데이터 및 별도 복원·결정 테이블을 포함하지 않았다. 격리 PostgreSQL에서 스냅샷 또는 이벤트가 남아 있는데 공간 삭제가 `completed`로 반환되는 문제를 재현했다. 운영 데이터 영향은 확인하지 않았다.
- 조치: 여섯 테이블 중 현재 공간에 하나라도 있으면 삭제와 복구 replay를 보수적으로 차단하고 UI에 미지원 사유를 표시한다. 기존 행은 삭제하지 않는다.
- 검증·한계: 격리 DB에서 재현 테스트가 차단으로 전환됐다. 미공개 trusted DB-client helper와 직접 SQL은 gate를 우회할 수 있어 동시 삽입 안전성은 미보장이다. 공개 연결 전에 별도 원자적 gate/fence가 필요하다.

사람이나 에이전트를 탓하기 위한 문서가 아니다. 확인된 사실과 가설·검증 여부를 구분하고, 각 항목을 해결 후에도 지우지 않고 갱신한다. 기록 규칙과 민감 정보 제외 기준은 [PR 운영과 실수 기록](PR_WORKFLOW.md)을 따른다.

### 2026-10-31 — 삭제 precursor 경합·rollback 시험의 잘못된 격리
- 맥락: PR #25 독립 리뷰에서 발견한 테스트 결함이다. 테스트 모형은 운영 보장이 아니다.
- 사실과 영향: 기존 경합 시험은 발급 promise를 시작한 뒤 실제 shared gate 대기를 확인하기 전에 잠금을 풀어 false green이 가능했다. rollback 시험의 고정 이름 trigger는 같은 DB의 다른 grant 갱신에도 오류를 유발할 수 있었다. 운영 경로 변경이나 실제 제품 데이터 영향은 확인되지 않았다.
- 원인: 요청 시작과 DB 잠금 대기를 혼동했고, 테스트 실패 주입의 식별자 및 영향 범위를 격리하지 않았다.
- 조치 및 재발 방지: 전용 연결의 서로 다른 backend PID, 동일 DB/gate의 exclusive 보유와 shared 미획득 및 차단 관계를 확인한 뒤에만 잠금을 푼다. 고유 trigger/function은 테스트 grant에만 적용하고 finally에서 정리하며 다른 공간 grant 갱신도 검증한다.
- 검증/상태: exclusive gate와 shared gate를 각각 임시 제거했을 때 대응 관측 assertion이 실패했고 즉시 원복했다. 복원 후 신규·기존 PostgreSQL 삭제 회귀 21건을 신규 DB에서 두 번 통과했고 Node 24 `npm run check`가 통과했다. 독립 재검토와 최종 CI는 별도다.

### 2026-10-31 — advisory 잠금 수명 구분에 대한 성급한 제안
- 맥락: 자격증명 삭제 후속 작업에서 coordinator가 `pg_locks`만으로 세션 및 트랜잭션 advisory 잠금을 구분할 수 있다고 제안했다가 정정했다.
- 사실과 영향: 실제 PostgreSQL의 같은 backend에서 두 종류의 exclusive 잠금은 키를 제외한 조회 필드가 같았다. 기존 구현이나 삭제 게이트는 이 가정에 따라 바꾸지 않았다. 해당 실험은 모든 PostgreSQL 버전과 다른 관측 방법을 검증한 것은 아니다.
- 원인: 잠금 보유 표시와 잠금 수명 증명을 혼동하고 제안 전에 실제 DB 동작을 확인하지 않았다.
- 조치 및 재발 방지: `pg_locks`만으로 잠금 수명을 판정하지 않는다. 전용 트랜잭션이 gate를 workspace 행보다 먼저 획득하고 종료까지 소유하는 대안을 검토하며, 보안·동시성 주장은 실제 DB 경합 시험과 독립 리뷰로 확인한다.
- 검증/상태: 격리된 PostgreSQL 세션의 조회 및 잠금 해제를 확인했다. 제안 대안의 구현·회귀와 운영 안전성은 별도 검증 대상이다.

### 2026-10-31 — assistant 세션 검증 누락과 해결 중단
- 맥락: OpenCode 2.2.2 익명화 응답 fixture의 수집·제외 경계 점검.
- 사실과 영향: assistant 응답에 세션 ID가 없는데 호출자의 문자열로 제외 여부와 저장 세션을 결정했다. 다른 문자열을 넣으면 제외 검사를 우회할 수 있음을 재현했다. 이전 점검에서 이 문제를 보고한 뒤 수정 없이 멈춰 사용자의 추가 지시가 필요했다.
- 원인: 응답과 세션 사이의 신뢰 가능한 결합을 검증하지 않았고, 안전상 차단 가능한 문제의 해결을 이어가지 않았다.
- 조치: 해당 형식을 신뢰 가능한 결합 구현 전까지 차단하고 수집 가능 목록에도 불가로 표시한다. 기존 성공 시험을 제거한 이유와 기능 축소는 fixture 설명에 명시한다.
- 검증: 실제 익명화 fixture의 위조 세션 요청은 수정 전 route 회귀에서 성공해 실패했고 수정 후 거부됐다. 최종 CI 및 실제 호스트 검증은 별도 확인이 필요하다.
- 상태/후속: 임시 fail-closed. 신뢰 authority의 artifact/세션 결합, 선택·제외·현재 권한 검증 및 실환경 검증은 후속 작업이다.
- 추가 검증 실수: 집중 테스트는 통과했으나 첫 `npm run check`에서 테스트 케이스의 `as const`가 배열을 readonly로 추론해 서버 타입 검사가 실패했다. mutable 옵션 타입을 명시하고 전체 검사를 다시 실행한다. 이 오류는 운영 코드 실행 결과가 아니다.
- 독립 리뷰 후 추가 발견: synthetic도 호출자가 세션·제외 목록·본문을 전부 작성할 수 있는데 이전 조치에서 정상 수집을 유지했다. 실제 fixture의 도구 텍스트를 synthetic으로 재포장한 HTTP 요청이 201로 저장됐고, 수동 입력에서도 수집 메타데이터를 위조할 수 있었다. 두 자동 형식 모두 차단하고 수동 입력의 위조 메타데이터를 거부한다. 이는 이미 가진 텍스트의 수동 등록 자체를 차단하거나 유출 방지를 보장하지 않는다. 최초 runtime HTTP 오류도 공통 매핑에서 503으로 숨겨져 명시 409와 한국어 설명으로 교체한다. 수정 전 RED 및 최종 회귀 결과는 PR에서 확인한다.
- 재검토 후 추가 발견: 수동 HTTP의 임의 `tool` 문자열을 허용해 수집 도구명으로 오인 가능한 출처가 저장됐다. 기존 인계의 메타데이터 위조 불가 표현은 과장이었다. 실제 HTTP에서 위조 도구명이 201로 저장되는 RED를 확인했고, 수동 API에서 `manual` 외 값을 거부한다. 직접 내부 서비스는 별도 신뢰 계약이다. 최종 회귀·CI는 PR에서 확인한다.
- 실제 runtime 수동 성공 회귀의 첫 실행은 macOS 임시 경로의 심볼릭 링크 때문에 `UNSAFE_STORAGE_ROOT`로 503이 발생했다. 기존 테스트처럼 실제 경로를 구해 안전한 root 검사는 유지하고 재실행한다. 수집 차단 테스트만으로 쓰기 경로를 확인한 것으로 판단한 것이 원인이다.
