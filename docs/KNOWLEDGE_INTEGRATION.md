# 개인 로컬 위키 → 지식 누적 순환: 통합 계획과 수용 기준

> **상태: 미래 설계 / 미구현 / 평가 미실행 (2026-10-29).** [North Star](LLM_WIKI_CORE.md)의 구현 경로를 구체화한다. [ADR 004](adr/004-unified-knowledge-service.md)는 아직 제안 상태다.

## 두 경로의 현재 상태와 핵심 차이

| 구현 | 검증된 로컬 개발 범위 | 아직 없는 범위 |
| --- | --- | --- |
| `src/domain/wiki.ts` + 웹 | 원본 기반 복수 페이지 변경 집합·승인/발행·인용 답변 재편입·Lint (브라우저 상태) | 운영 ACL·서버 DB 원자성·의미 품질 검증 |
| `scripts/wiki-connector/` + MCP | 개인 JSON 작업본·연결 중 동기화·충돌 보존·단일 페이지 공유 제안 (합성 서비스) | 원본 등록·지식 종합·질문 재편입·Lint·운영 인증 |
| 공통 지식 서비스 (목표) | 없음 | 웹·MCP·개인 작업본이 같은 원본/지식/검토/발행/권한 계약 사용 |

동기화는 **전달과 편집**, 지식 컴파일은 **기존 결론과 연결을 근거에 따라 발전**시키는 동작이다. 어느 한쪽의 성공으로 다른 쪽을 완료했다고 표시하지 않는다.

## 목표 수직 경로

```text
허용된 원본/실행 증거
    → 원본 스냅샷·버전·접근 범위 고정
    → 관련 기존 발행 지식 식별
    → Ingest: 조건·연결·복수 페이지 변경 집합 제안
    → 근거/권한/기준 검증 → 검토 → 일관된 발행 → Lint
    → 웹/API/MCP 및 허용된 개인 로컬 작업본에서 조회
    → 에이전트가 사용 버전·환경을 확인하고 업무 수행
    → Query 결과/관측/반증을 변경 후보로 등록 → 재검토
```

개인 동기화가 원본을 등록하거나 Ingest를 자동 실행하는 것은 아니다. 공유 지식 정본과 원본 증거의 권위는 서버가 가진다. 개인 작업본·공유 페이지·Raw Source는 별도의 데이터 유형이어야 한다.

## 변경 시 유지할 데이터·보안 계약

| 경계 | 보존해야 할 구분 | 실패 형태 |
| --- | --- | --- |
| 식별자 | 공간+페이지+버전, 개인 revision, 원본 ID+버전 | 공간이 다른 같은 ID끼리 출처/본문 혼동 |
| 출처 | 검증된 Raw Source vs `sourceRefs` ID/버전/위치 vs 파생 답변 | 출처 참조 문자열·자기 인용을 독립 증거로 오인 |
| 권한 | 읽기 허가 vs `localCopyAllowed` vs 공유 권한 | 제한 원본·파생 내용의 로컬/공유 유출 |
| 변경 | 개인 draft/동기화 버전 vs 공유 기준 vs 복수 페이지 변경 집합 | 의도치 않은 최신 개인본 제출, 부분 발행 |
| 승인 | 제안 해시·정책 버전 vs 발행 직전 상태 | 승인 후 변경·철회를 몰래 반영 |
| 시간/경험 | 유효 시점·환경 vs 관찰/검증 시점, 실행 증거 vs 추론 | 오래된 규칙이나 미검증 교훈 공식화 |

현행 `validatePage`의 `sourceRefs`에는 `id/version/location`만 있고 원본 본문·원본 검증 결과는 없다. 현행 `wiki_propose_change`는 **선택한 개인 revision의 단일 페이지**를 공유로 제안하며, `src/domain/wiki.ts`의 의존 변경 집합과 통합돼 있지 않다. 향후 DTO와 도구 의미를 바꿀 때는 버전/마이그레이션/호스트 호환성을 별도 결정한다.

## 단계별 다음 개발 (일정 확정 아님)

1. **P0 공통 계약:** Source/Knowledge/Personal Draft/Proposal Batch/Outcome Evidence의 소유·권한·버전/철회 관계와 ID 체계, ADR 004 채택 여부를 검토한다.
2. **P1-a 정본 연결:** 웹과 개인 MCP가 공통 서버의 같은 발행본/권한/버전 규칙을 사용하도록 연결한다. 개인→공유는 **제안**으로 전환하고 의존 변경 집합의 원자 발행 전에는 부분 자동 발행을 막는다.
3. **P1-b 실제 누적:** 원본 등록 → 기존 지식과 종합 → 검토·발행 → 인용 Query → 결과 재편입 → Lint를 실제 모델·서버 저장소에서 통합한다. 실패/미구현 상태를 숨기지 않는다.
4. **P2 검증과 정련:** 정정/철회 영향 분석, 조건·시간, 지속 작업/복구, 결과 환류와 [EVALUATION](EVALUATION.md)의 대조 실험을 실행한다.

K8s 초기 운영 경계와 실제 자료/보안 게이트는 [배포 계획](K8S_RELEASE.md)을 따른다. 이 문서는 기술 스택·개인/팀/전사 계층·자동 공식화 정책을 확정하지 않는다.

## 통합 수용 시나리오 (KI-01~08: 전부 미실행 설계)

| ID | 상황 | 기대 결과 / 실패 조건 | 관련 기존 기준 |
| --- | --- | --- | --- |
| KI-01 개인과 공유 분리 | `wiki_write` → `wiki_sync` | 개인본 동기화만 수행. 공유 발행/원본 검증/컴파일했다고 표시하면 실패 | GOV-003/004, KE-08 |
| KI-02 참조와 원본 구별 | 페이지 `sourceRefs`에 존재하지 않거나 무권한인 원본 ID 추가 | 서버 원본/위치/권한 확인 없이는 공식 주장으로 발행 거부 | CORE-002, KNO-002/003 |
| KI-03 기존 지식 재구성 | 기존 주제·개념과 관련된 새 근거/반증 등록 | 관련 결론·조건·연결을 재검토하는 복수 페이지 변경 후보. 새 파일 추가만으로 통과 불가 | CORE-003/004, KE-01/02 |
| KI-04 일관된 공유 제안 | 특정 개인 revision 선택 후 공유 기준 변경·의존 페이지 2개 | 선택 revision·승인한 해시 고정, 한 항목 충돌 시 전체 발행 차단. 현행 단일 페이지 커넥터만으로 통과 주장 금지 | REV-004~006, KE-08 |
| KI-05 질의와 결과 환류 | 버전 고정 인용 답변+업무 검증 결과 | 파생 지식을 새 독립 증거로 세지 않으며 변경 후보로 등록. 원본 변경 시 재평가 | CORE-005/006, KE-05/06 |
| KI-06 공간·기기·권한 철회 | 같은 pageId의 여러 공간, 기기 간 충돌, 접근 철회 | 정체성·양쪽 충돌 보존, 권한 불명 시 캐시 열람 거부. 누출은 안전 실패 | ACL-004~009, KE-07/08 |
| KI-07 실패와 재시도 | 모델 미연결, 발행 응답 소실, 정책 버전 변경 | 가짜 의미 검증/성공 금지, 중복 발행 차단, 정책 변경 시 재검토 | CORE-008, JOB-002 |
| KI-08 에이전트 성과 | 원본만/정적 위키/유지 위키를 동일 모델·예산·권한으로 비교 | 조건·근거 정확도/작업 성공률·비용·안전 회귀를 사전 확정 지표로 평가. 동기화·페이지 수로 대체 불가 | CORE-012, EVA-001~010 |

이 KI는 **통합 설계 검사 ID**이며 새 제품 요구사항이나 합격 결과가 아니다. 기존 Node/HTTP/MCP 테스트는 일부 동기화·충돌 행동을 확인할 뿐 운영 서비스·지식 의미 품질 검증을 대신하지 않는다. 기존 KE-01~08은 [평가 계약](EVALUATION.md)에 있다.

## 코딩 에이전트의 설계 판단

새 기능/PR에서 필요한 항목만 답한다. 동일한 North Star 본문을 매번 복사하지 않는다.

1. 변경 위치는 단순 전달/저장인가, 지식의 종합/진화인가?
2. Raw Source, 개인 작업본, 공유 발행본의 정본과 권한은 어디인가?
3. 기존 결론·연결·파생 계보가 어떤 원본 버전에서 달라지는가?
4. 공간 충돌, 원본 철회, 검토 이후 변경, 재시도/모델 오류를 어떻게 처리하는가?
5. 어떤 KI/KE 시나리오로 검증하고 실제 실행과 미실행을 어떻게 구분하는가?

[업무 에이전트 인터페이스](AGENT_INTERFACE.md)와 [아키텍처](ARCHITECTURE.md)를 함께 참고한다. 이 설계 문서는 `wiki/SCHEMA.md` 런타임 정책이나 [North Star](LLM_WIKI_CORE.md)의 의미를 자동 수정하지 않는다.
